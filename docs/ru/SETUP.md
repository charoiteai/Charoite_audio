# Установка и первый запуск

*[English](../SETUP.md) · **Русский** · [中文](../zh/SETUP.md)*

## 1. Зависимости

**Из готового приложения (рекомендуется).** Charoite.app из
[релиза](https://github.com/charoiteai/Charoite_audio/releases) несёт
python-контур внутри: ни git clone, ни venv, ни pip. Нужна только языковая
модель — Ollama:

```bash
brew install ollama
brew services start ollama
ollama pull qwen3.6:35b-mlx && ollama pull qwen3.5:4b && ollama pull gemma4:e4b
```

**Ставьте что-то одно: либо brew, либо Ollama.app — не оба.** Приложение
поднимает свой сервер и занимает порт 11434; brew-сервис после этого не
стартует и молча висит в `error`, а обновление brew-версии не применяется —
сервер остаётся старым. Диагноз выглядит безобидно: `ollama --version` пишет
предупреждение о несовпадении версий клиента и сервера. Если приложение уже
стоит, а вы хотите brew: закройте его, отключите автозапуск
(`launchctl disable gui/$(id -u)/com.ollama.ollama`) и удалите — сервис
поднимется сам.

⚠️ **Прокси.** Ollama читает `HTTP_PROXY`/`HTTPS_PROXY` из окружения, а не
системные настройки macOS. Сервис из-под `brew services` их не наследует и
ходит напрямую — на замере 13.08 это 6,8 МБ/с против 39 КБ/с через локальный
прокси, разница в сто семьдесят раз. Если вы всё же запускаете `ollama serve`
руками из терминала с настроенным прокси, модели будут качаться часами.

Всё остальное приложение спросит и сделает само: имя и папку графа — в мастере
первого запуска, модель разделения голосов — кнопкой, разрешения — системными
диалогами.

**Из исходников** (разработка, своя сборка, не-Apple Silicon):

```bash
git clone https://github.com/charoiteai/Charoite_audio && cd Charoite_audio
python3 -m venv .venv && .venv/bin/pip install .
cp config/config.example.yaml config/config.yaml
```

Приложение берёт вложенный контур, если он есть, и `.venv` рядом с
репозиторием — если нет. Своя сборка бандла с контуром:
`scripts/build_embedded_python.sh && app/make_app.sh`.

Какие именно модели — приложение предложит само: мастер первого запуска
смотрит объём памяти вашей машины и показывает три готовых набора
(«Полный», «Сбалансированный», «Лёгкий») с пометкой рекомендованного, а
выбранный записывает в конфиг и качает одной кнопкой. Подробности о
моделях — в [MODELS.ru.md](MODELS.md).

## 2. Конфиг: два обязательных поля

**Проще всего — в приложении.** Мастер первого запуска спрашивает имя и папку
графа и сам пишет их в `config/config.yaml`; папка выбирается панелью. Файла
ещё нет — мастер создаёт его из образца в поставке и сам размечает каталог
`config/`. Если записать не удалось (нет прав на папку данных, испорченная
установка без образца), мастер прямо скажет об этом с причиной, а не покажет
«Сохранено»: молчаливый отказ здесь означал бы, что человек настроил в
пустоту и упёрся в вечно красную готовность. Правка файла руками ниже — для
тех, кто ставит без интерфейса.

В `config/config.yaml`:

- `sufler.user_name` — ваше имя. Им подписывается ваш микрофон в стенограмме,
  и его никогда не присвоит другой голос.
- `sufler.graph_dir` — папка графа знаний (пусто = граф выключен, работает
  только транскрибация). Укажите путь внутри вашего Obsidian-vault, например
  `~/Documents/Obsidian/Work` — Чароит создаст структуру сам.

Полезно заполнить `sufler.user_context` (кто вы по работе, 1-2 предложения) —
это контекст для мгновенных ответов.

## 3. Системный звук (звонки) — одно разрешение и перезапуск

Приложение само захватывает звук встречи средствами macOS (ScreenCaptureKit).
При первой записи система один раз спросит разрешение «Запись экрана и
системного звука» — нажмите «Разрешить», **а затем перезапустите Чароит**.

Перезапуск обязателен, и это не наша прихоть: macOS применяет выданное право
только к новому запуску процесса. Пока приложение не перезапущено, галочка в
системных настройках уже стоит, а захват всё ещё не работает — эта встреча
запишется без второй стороны. Готовность в мастере первого запуска покажет
отдельной строкой, что перезапуск нужен.

После перезапуска — всё: драйверы, Audio MIDI Setup и переключение выхода не
нужны, звук продолжает идти в колонки как обычно, а на macOS 15 и новее тем
же потоком приходит и микрофон.

Раздельные каналы дают бесплатную диаризацию «вы/собеседники» и фильтр эха.

**Запасной путь — BlackHole** (macOS до 13 или отказ в разрешении):

1. Установите [BlackHole 2ch](https://existential.audio/blackhole/).
2. Audio MIDI Setup → «+» → Multi-Output Device → отметьте динамики И BlackHole.
3. Выход системы → этот Multi-Output (звук слышен и попадает в Чароит).

Чароит выбирает источник сам: ScreenCaptureKit, затем BlackHole. В статусе
встречи видно, какой канал взят.

## 4. Права macOS

- **Микрофон** — запросится при первом запуске.
- **Запись экрана и системного звука** — запросится при первой записи встречи;
  без неё слышен только микрофон (или BlackHole, если он настроен).
- **Universal Access** (опционально) — только для системной вставки диктовки
  (⌘V за вас); без него текст просто остаётся в буфере обмена.

## 5. Диаризация голосов (опционально)

Положите ERes2Net-эмбеддер в `models/diar/embedding.onnx` —
инструкция в [DIARIZATION.ru.md](DIARIZATION.md). Без него метки идут
по каналам (вы/собеседник), с ним — по голосам («Собеседник 1/2/…»).

## 6. Запуск

```bash
.venv/bin/python src/main.py        # CLI: живая стенограмма + подсказки
# или демон для интеграции с UI (NDJSON stdout/stdin):
.venv/bin/python src/daemon.py
```

Первый запуск скачает STT-модель (~1 мин). Скажите что-нибудь — строки
стенограммы появятся в консоли.

Успешная первая проба должна закончиться карточкой встречи, а не только
появлением файла стенограммы. Полный проверочный путь описан в
[практическом руководстве](USER_GUIDE.md), а карта временного аудио,
стенограмм, графа и сроков хранения — в
[«Данные и восстановление»](DATA_AND_RECOVERY.md).

## 7. Что где лежит

- `transcripts/` — стенограммы и рабочие файлы встречи
- `recordings/` — полные записи (автоудаление через `record_keep_days`)
- `<graph_dir>/Встречи-архив/` — папка «дата — название» на каждую встречу:
  Саммари, Минутки, Стенограмма, Вопросы-ответы, Разбор

Это краткая карта. Там, где важны срок удаления, источник истины и порядок
восстановления после сбоя, используйте
[подробную карту данных](DATA_AND_RECOVERY.md).

## Проблемы

- **Пустая стенограмма** — проверьте вход: `python -c "import sounddevice as sd; print(sd.query_devices())"`.
- **Медленные ответы** — `ollama ps`: модель должна держаться в RAM;
  проверьте, что в конфиге не убран `num_ctx: 8192`.
- **Нет системного звука** — проверьте разрешение: Системные настройки →
  Конфиденциальность → Запись экрана и системного звука, Чароит должен быть
  в списке и включён. После смены версии приложения разрешение иногда нужно
  выдать заново: снимите галочку и поставьте снова. Если пользуетесь
  BlackHole как запасным путём, выходом macOS должен быть Multi-Output, а не
  динамики напрямую.

## Семантический поиск (рекомендуется)

Поиск по архиву в приложении добавляет семантический слой, когда в
Ollama есть эмбеддинг-модель `bge-m3`:

```bash
ollama pull bge-m3   # ~1.2 ГБ; без неё поиск чисто лексический
```

Индекс строится фоном при первом поиске и обновляется инкрементально
(хранится в `~/Library/Application Support/Charoite/semantic_index_v2.bin`).

## Диагностика

`python3 scripts/doctor.py` проверяет Python, зависимости, ключи конфига, папку графа, Ollama и модели (включая `bge-m3`), диаризацию — с точным рецептом для каждой проблемы.

Вторая половина отчёта — про работу, а не про установку: отвечает ли модель на **генерацию** (у вставшей Ollama список моделей приходит мгновенно, а инференс стоит — и это единственный способ отличить одно от другого), не застряли ли встречи по дороге в граф, сколько файлов ждёт в папке импорта и сколько осталось места. Первый вопрос при любом «Чароит молчит» — сюда.

Доктор — единственный скрипт, который работает любым питоном: он написан без
зависимостей, чтобы отвечать до их установки. Всё остальное запускается через
`.venv/bin/python` — и если запустить системным, ответом будет строка с
рецептом, а не трассировка (`src/deps.py`).

## Версии: приложение, код и выпуск

В установке из репозитория живут три разные вещи, и расходятся они молча.
Приложение (`.app` в `~/Applications`), код в рабочей папке — на нём
работают демон и ночной цикл — и последний выпуск на GitHub. Приложение
0.46.0 при уже вышедшей 0.47.0 выглядит совершенно нормально; папка,
отставшая на десяток коммитов, — тоже. Понимаешь это, когда полдня чинишь
ошибку, которой в свежем коде нет.

Приложение сверяет все три и говорит на «Сегодня», если они разошлись.
Совпадение — норма, о ней строки нет: напоминание о норме перестают читать
за неделю. Версию кода берём из git-тега рабочей папки, номер выпуска — одним
GET к публичному API GitHub раз в сутки: без токена, без единого байта о вас,
и молча при любой ошибке сети. Не нужно — `sufler.check_updates: false` в
конфиге; общий рубильник `CHAROITE_NO_CLOUD` выключает и эту проверку.

## Ночной цикл (опционально)

`scripts/nightly.sh` приводит граф в порядок, пока вы спите: Tier-3
ревизия ядер (дубли, слияния — с бэкапами), утренний бриф `_Сегодня.md`
(готовый контекст дня) и бенч памяти (сигнал деградации качества).
Цикл ждёт, пока закончится разбор встречи, и работает на одной модели.
12.08 они совпали: транскрипция, ревизия ядер и сборка досье одновременно —
свободной памяти 14 ГБ из 64 при 17 ГБ уже в компрессоре. Локальный сервер
начал выгружать и грузить модели по кругу (41 раз за прогон), запросы стали
висеть по 2-6 минут, а потом он лёг совсем: 258 тем ушли без разбора.
Ожидание ограничено часом (`NIGHTLY_WAIT`, секунды): пропустить ночь целиком
хуже, чем поработать в тесноте.

Порядок шагов выбран так, чтобы бриф был к утру при любом раскладе: он пишется
сразу, до тяжёлых шагов, и ещё раз в конце — поверх причёсанных ядер. 13.08
это стоило целого утра: граф дорос до трёх сотен ядер, полная ревизия шла пятый
час, а бриф ждал своей очереди последним. Теперь по будням ревизия идёт
инкрементально (`--since-last`: только ядра, изменившиеся с прошлого прогона),
полная сверка — по воскресеньям или руками, `NIGHTLY_TIER3_FULL=1`.

Планируется через launchd:

```xml
<!-- ~/Library/LaunchAgents/ai.charoite.nightly.plist -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>ai.charoite.nightly</string>
  <key>ProgramArguments</key>
  <array><string>/bin/bash</string><string>/ПУТЬ/К/Charoite_audio/scripts/nightly.sh</string></array>
  <key>StartCalendarInterval</key><dict><key>Hour</key><integer>4</integer><key>Minute</key><integer>15</integer></dict>
  <key>StandardOutPath</key><string>/tmp/charoite_nightly.log</string>
  <key>StandardErrorPath</key><string>/tmp/charoite_nightly.log</string>
</dict></plist>
```

```bash
launchctl load ~/Library/LaunchAgents/ai.charoite.nightly.plist
```

Прошёл ли цикл — видно в приложении на вкладке «Сегодня», внизу колонки
недавних встреч. Ночная работа невидима по определению: человек спит, а
утром граф либо причёсан, либо нет — и по внешнему виду это не отличить.
Поэтому скрипт кладёт итог в `logs/nightly.json` рядом с данными (лог
launchd лежит в `/tmp` и исчезает при перезагрузке, по нему «не
запускалось» неотличимо от «файл стёрся»), а приложение читает файл и
показывает строку. Успешный прогон — одна спокойная строка со временем;
идущий прямо сейчас, упавшие шаги, оборванный прогон и пропущенная ночь
подсвечены.

Успехом считается только ночь, в которой не отвалилось ничего. Отдельно
ловится молчащая модель: если локальный сервер лёг посреди прогона, досье
собираются вхолостую — темы остаются без разбора, а шаг заканчивается
нулём. Такая ночь помечается «досье(модель-молчала)», иначе граф черствеет
незаметно.

Отдельно проверьте, на какой путь смотрит агент: если репозиторий
переезжал, `plist` продолжает запускать скрипт со старого места — ночью
граф правится прошлой версией кода, и увидеть это без статуса нельзя.
