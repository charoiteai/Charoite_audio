# Релизы

*[English](../RELEASING.md) · **Русский** · [中文](../zh/RELEASING.md)*

Версии и `CHANGELOG.md` автоматизированы через
[release-please](https://github.com/googleapis/release-please). Changelog
руками не правится никогда — пишите conventional-коммиты `fix:`/`feat:`,
остальное происходит при мёрдже в `main`.

## Как это работает

1. Каждый пуш в `main` запускает workflow `release-please`.
2. Он собирает коммиты `fix:`/`feat:` с последнего релиза в **релизный
   PR** с заголовком `chore(main): release X.Y.Z`, обновляя `CHANGELOG.md`
   и `.github/.release-please-manifest.json`.
3. Мёрдж этого PR ставит на коммит тег (`vX.Y.Z`) и создаёт GitHub Release.

Текущая версия живёт в `.github/.release-please-manifest.json`, а не в
`version.txt` в корне репо. Источник истины — git-теги.

## Squash-мёрджи: заголовок PR И ЕСТЬ коммит

При squash-мёрдже в `main` попадает ровно один коммит, и его subject —
это **заголовок PR**. Если заголовок не в conventional-формате
(`fix: …`, `feat: …`), release-please вообще не видит работу: ни
релизного PR, ни записи в CHANGELOG, ни бампа версии. Мы наступили на
это четыре раза за один день (#83–#86 смёрджены как `Fix/<имя ветки>`) —
целый день отгруженных фиксов остался невидим для changelog.

Правила:

1. Правьте заголовок в диалоге мёрджа до conventional-формата, прежде
   чем подтверждать squash.
2. Один PR с несколькими видимыми пользователю изменениями: добавьте в
   **тело** squash-коммита дополнительные простые строки
   `fix(scope): …` (без буллетов `* ` — строки-списки не парсятся) —
   release-please зарегистрирует каждую строку отдельной записью.
3. Уже смёрджили с плохим заголовком: запушьте коммит-носитель, в чьём
   сообщении лежат пропущенные conventional-строки (пустой коммит с
   машины мейнтейнера или небольшая реальная правка через PR).

## Разовая настройка: RELEASE_PLEASE_TOKEN

Релизный PR должен создаваться **personal access token**, а не
встроенным `GITHUB_TOKEN`. GitHub намеренно не запускает CI на ветках,
созданных встроенным токеном (защита от зацикливания), поэтому релизный
PR висел бы в `BLOCKED` без обязательных проверок. PAT делает ветку
«человеческой», и `lint`/`analyze` запускаются как обычно.

Настройка (владелец репо, один раз):

1. Создайте **fine-grained PAT**, ограниченный этим репо, с правами:
   - **Contents: Read and write** (тег + коммит changelog)
   - **Pull requests: Read and write** (открытие релизного PR)
2. Добавьте его секретом репозитория с именем **`RELEASE_PLEASE_TOKEN`**
   (Settings → Secrets and variables → Actions → New repository secret).

Пока секрета нет, workflow откатывается на `GITHUB_TOKEN`, так что
ничего не ломается — релизному PR просто нужен ручной «Approve and run»,
пока PAT не появится.

## Бандл приложения на каждый релиз

`release-app` собирает на macos-раннере `Charoite.dmg` (установщик для
первой установки), `Charoite.app.zip` (им обновляется уже установленное
приложение) и `.sha256` к обоим — без опубликованной суммы обновление внутри
приложения отказывается ставить скачанное. Прикрепляет всё к релизу. Три
триггера:

- `workflow_run` после workflow `release-please` — основной путь.
  release-please публикует релизы под `GITHUB_TOKEN`, а защита GitHub от
  рекурсии означает, что такие события НЕ порождают `release: published`
  в других workflow (v0.19.0 сначала вышел без бандла — так мы это и
  узнали). Джоба продолжается, только когда release-please завершился
  со статусом **succeeded** (`completed` приходит и после упавшего
  запуска).
- `release: published` — оставлен для релизов, созданных человеком.
- `workflow_dispatch` со входом `tag` — ручная перезаливка для старого
  релиза (см. постмортем v0.19.0 ниже). Ручные запуски всегда
  пересобирают и перезаписывают ассет (`--clobber`).

Порядок шагов в джобе не случаен: **первый** шаг выясняет, какому тегу
нужен ассет и не существует ли он уже — до любой сборки.
`release-please` завершается на каждом пуше в `main`, обычно без
создания релиза, поэтому большинство цепных запусков должны обрываться
за секунды на шаге резолва, а не после полной сборки под macOS.

Сборка чекаутит `refs/tags/<tag>` — **код именно этого релиза, а не
верхушку `main`**. `make_app.sh` проставляет версию из `git describe`,
который на чекауте тега даёт ровно этот тег, так что
`CFBundleShortVersionString` совпадает с релизом. Чтобы `git describe`
видел теги, нужен полный чекаут (`fetch-depth: 0`).

Проверка после любых изменений здесь: скачать ассет, `ditto -x -k`,
`codesign -dv`, убедиться, что `CFBundleShortVersionString` совпадает с
тегом.

## Постмортем: двойной сбой v0.19.0

На одном релизе сошлись два дефекта:

1. v0.19.0 вышел без бандла (урок про защиту от рекурсии выше).
2. Первый фикс резолвил тег через `gh release list --limit 1`, но
   собирал **текущий `main`** — у чекаута не было `ref`. К моменту
   мёрджа самого фикса `main` уже ушёл вперёд тега `v0.19.0`, и к
   старому тегу прикрепилась сборка более нового кода. Скачавшие
   «0.19.0» получали бандл с кодом новее релиза, при этом `Info.plist`
   всё это время заявлял 0.19.0 — `git describe` на `main` по-прежнему
   резолвился в последний тег.

Родившийся из этого инвариант — *ассет собирается из кода собственного
тега* — теперь закреплён в `tests/test_workflows.py`, а workflow
чекаутит тег явно.

**Перезаливка правильного ассета 0.19.0:** Actions → release-app →
Run workflow → `tag: v0.19.0`. Ручной запуск пересобирает из тега
`v0.19.0` и заменяет неверный ассет (`--clobber`). Дальше проверка как
выше: распакованное приложение должно показывать
`CFBundleShortVersionString` 0.19.0.


## Защита ветки: что блокирует мёрж и почему

Обязательные проверки на `main` — **`lint`** и **`pytest (src/)`**. За этим
коротким списком два осознанных решения.

**Тесты теперь блокируют мёрж.** Раньше не блокировали: обязательными были
`lint` и `analyze`, поэтому красный `pytest` мёржился без возражений. Все 123
теста были совещательными, включая сторожей, которые держат обещания о
приватности.

**`analyze` (CodeQL) — совещательный, не обязательный.** Он запускается по
событию `pull_request`, а для PR, конфликтующего с `main`, GitHub не создаёт
merge-ref — и не запускает ни одного `pull_request`-workflow. Обязательный
контекст в таком случае не приходит никогда, и PR вечно висит на «Expected —
Waiting for status to be reported», причём перезапускать нечего. Ровно в этом
была история «фантомных чеков», которые лечились пересозданием ветки от `main`.
`lint` и `pytest` идут ещё и по `push`, поэтому их контексты есть даже у
конфликтного PR.

**`strict` (требовать актуальности ветки) выключен.** При четырёх релизах за
день каждый мёрж в `main` отправлял все открытые PR в BEHIND, а
`required_linear_history` делал лечением ребейз — новые SHA, все проверки
заново, свежий шанс на конфликт. Он покупает защиту от семантических
конфликтов, которую здесь всё равно ничто не реализует.

**`swift test (app)` и `build (app-ios)` остаются совещательными**, пока у их
workflow стоит фильтр `paths:`. Обязательная проверка, которая не стартует на
PR без Swift-правок, подвесила бы его точно так же, как `analyze`.

## Подпись манифеста обновлений (после каждого релиза)

Апдейтер не ставит выпуск без подписи манифеста ключом владельца — якоря,
независимого от GitHub (карточка №24): контрольная сумма лежит рядом с
архивом, и кто дотянулся до релиза, подписал бы и её. Ключ в CI не бывает.

После публикации релиза (release-please + release-app) — одна команда с
машины владельца (нужен `gh` ≥ 2.28 — флаг `--latest`):

    .venv/bin/python scripts/sign_release_manifest.py vX.Y.Z

Она смотрит состояние релиза, скачивает `Charoite.app.zip`, распаковывает
и СВЕРЯЕТ подпись бандла (codesign --strict, команда AR7PDJQNR4) —
подложенный до подписи чужой архив получает отказ, а не подпись владельца.
Затем строит манифест `<версия>  <sha256>` САМА (версию несёт подписанный
файл — голый хеш позволял реплей старой тройки под новым тегом),
подписывает его сырые байты (raw ed25519 → base64) ключом
`~/.config/charoite/update_manifest_ed25519.pem`, прикладывает
`Charoite.app.zip.manifest` + `.manifest.sig` к релизу и последним шагом
снимает флаг pre-release (`gh release edit --prerelease=false --latest`).

### Гейт: выпуск без подписи не бывает latest (PR #375)

Апдейтер спрашивает `/releases/latest`, куда GitHub pre-release не отдаёт.
Поэтому релиз держится pre-release, пока владелец не подписал, — с двух
сторон:

- **release-please** создаёт каждый выпуск как pre-release
  (`"prerelease": true` в `.github/release-please-config.json`) — окна
  нет вовсе. Формула release-please: `prerelease && (суффикс версии ||
  major == 0)` — на 0.x работает сама, с 1.0.0 перестанет; тест-растяжка
  `test_release_gate_tripwire_pre_major_versions_only` упадёт на первой
  версии ≥ 1.0, чтобы это решили осознанно (остаётся CI-гейт с окном в
  латентность Actions), а не потеряли молча.
- **release-app** (CI) — страховка на всё остальное. В начале прогона:
  стабильный релиз без `.manifest.sig` переводится в pre-release
  (ручной релиз, снятый рукой флаг, 1.0+); триггер слушает и `released`,
  чтобы поймать флаг, снятый в веб-интерфейсе. После каждой сборки:
  прежние `.manifest`/`.manifest.sig` снимаются (они подписывали ДРУГОЙ
  архив и больше не сходятся), релиз — pre-release до новой подписи.
  `.manifest` CI не кладёт: без подписи он приложению бесполезен.
- **Скрипт подписи** ведёт себя по состоянию релиза. Pre-release и не
  подписан — обычный путь. Стабильный и подписанный — повторная подпись:
  на время замены пары релиз прячется в pre-release (два upload не
  атомарны, между ними апдейтер увидел бы манифест с чужой подписью).
  Стабильный и НЕ подписанный — гейт не сработал: скрипт всё равно
  подписывает (пользователи и так заблокированы), но кричит в stderr и
  выходит с кодом 3 — разобраться, откуда релиз. `--latest` ставится
  только если тег не старше нынешнего latest: подпись исторического
  v0.57.0 после v0.58.0 не откатывает `/releases/latest`.

Пока владелец не подписал — пользователи остаются на предыдущем выпуске;
упала загрузка подписи или снятие флага — релиз остаётся pre-release,
скрипт печатает команду для повтора. Ручной `gh release edit --latest` в
обход скрипта — ровно то, от чего гейт защищает: не делать (CI вернёт
pre-release при следующем событии, но окно до этого — ваше).

Потерян приватный ключ — обновления встанут у всех: новую пару генерирует
владелец, публичная половина меняется в `UpdateAuthenticity.swift`
(константа `manifestKeyBase64`), выпускается новый релиз.
