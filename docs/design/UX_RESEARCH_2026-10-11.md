# Чароит: исследование пользовательских сценариев и практик UX

Дата: 11 октября 2026. База исходников: `5149770552b2b49c8b48dec12ad44a8351028cbf`.

## Вывод

Наиболее полезная следующая работа — укрепить контроль пользователя над
записью, черновиками, историей, поручениями и происхождением ответа.
Переход на новую UI-библиотеку сейчас не решает найденные проблемы:
они находятся в обработчиках действий, семантике статусов и компоновке
существующего SwiftUI. Это инженерная оценка по коду, а не измеренное
предпочтение пользователей.

Исследованы основные пути «Сегодня → запись → результат → поручения →
вопрос к памяти», первый запуск, импорт и библиотека. Метод: чтение
представлений и сервисов, разбор ветвей отказа, сопоставление с первичными
источниками. Живой macOS-прогон, замеры удобства и интервью здесь не
проводились. Утверждения о кликах, контрасте и времени выполнения требуют
отдельной проверки.

## Практики и источники

| Источник | Практика | Применение в Чароите |
| --- | --- | --- |
| [Apple: Searching](https://developer.apple.com/design/human-interface-guidelines/searching) | Понятная область поиска, заметный вход и средства уточнения | Объяснить, ищет ли строка по архиву или спрашивает модель; отличать отказ от отсутствия результатов |
| [Apple: Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) | Предупреждать перед редким действием, которое нельзя отменить | Очистка сохранённой истории чата требует явного подтверждения; обычные обратимые действия не должны плодить диалоги |
| [Apple: Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo) | Предсказуемое восстановление после действия | Для отметки поручения перспективнее отмена, чем подтверждение каждого чекбокса |
| [Apple: Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) | Выбирать индикатор по наличию измеряемого прогресса | Показывать реальные стадии/части обработки; не придумывать процент или время окончания |
| [Apple: Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards) | Сохранять привычные команды и ограничивать нестандартные сочетания | Проверить Cmd-F в библиотеке/задачах, Cmd-Enter в чате и полный доступ без мыши |
| [Apple: ViewThatFits](https://developer.apple.com/documentation/swiftui/viewthatfits) | Нативный выбор подходящей компоновки из нескольких вариантов | Вопросы-подсказки чата переносить из ряда в столбец, когда ширины недостаточно |
| [Microsoft Research: Human–AI interaction](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/) | Объяснять возможности и ограничения ИИ, поддерживать исправление ошибок и контекст действий | Не выдавать материалы контекста за проверенные цитаты; не объявлять удалённый ответ локальным |
| [NN/G: Empty states](https://www.nngroup.com/articles/empty-state-interface-design/) | Объяснять причину пустоты и конкретный следующий шаг | Разные тексты для первого запуска, пустого дня, отсутствия совпадений и ненастроенной памяти |
| [NN/G: Visibility of system status](https://www.nngroup.com/articles/visibility-system-status/) | Своевременная обратная связь о результате действия | Сохранять вопрос, который сервис не принял; сообщать о записи и обработке на том же экране |
| [W3C: Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | Статус должен быть доступен вспомогательным технологиям без принудительного переноса фокуса | Использовать как ориентир проверки VoiceOver; это веб-рекомендация, не заявление о соответствии нативного приложения WCAG |

Все рекомендации выше пересказаны. Их применение к конкретным экранам —
решение этого аудита; источники не исследовали Чароит и не доказывают,
что предложенная компоновка уже стала удобнее.

## Найденные проблемы и решения

| Приоритет | Наблюдение по коду | Решение / состояние |
| --- | --- | --- |
| P1 | `LocalChatView.submit` очищает draft после `send`, но сервис отклоняет отправку во время streaming. `onSubmit` доступен независимо от disabled-кнопки | В этой ветке: `send` возвращает факт принятия; draft очищается только при принятии |
| P1 | `clear` удаляет историю и сразу сохраняет пустой массив; кнопка мусорной корзины вызывает его напрямую | В этой ветке: подтверждение с указанием области удаления и отсутствия отмены; Cancel сохраняет историю |
| P1 | `llm.allow_remote` разрешает другой хост, но чат показывает «0 запросов в сеть», а metaLine всегда «локально» | В этой ветке: убран неподтверждённый сетевой счётчик; адрес генерации фиксируется до асинхронного поиска, мета различает локальный/другой сервер |
| P1 | Шапка задач включает название, сводку, сегменты, поле 210 pt, checkbox и две кнопки в одной строке при минимуме detail 640 pt | Отдельная ветка задач: сводка и действия сверху, группировка/поиск/checkbox отдельной строкой, гибкая ширина поиска |
| P2 | В drawer чата 430 pt шапка складывает fixedSize-заголовок, picker 150 pt, чип памяти и кнопки | В этой ветке: две строки управления и отдельный статус; вопросы-подсказки используют ViewThatFits |
| P2 | Чипы берутся из результатов поиска, переданных модели, а не из сопоставления утверждений ответа с документами | В этой ветке: подпись «Материалы, переданные модели». Проверка утверждений и цитат — следующий отдельный проект |
| P2 | Чат прокручивается вниз при каждом изменении последнего ответа | Не менять вслепую. Проверить чтение старых сообщений во время генерации; затем автоскролл только при нахождении у нижней границы, иначе кнопка новых сообщений |
| P2 | После завершения поручение может исчезнуть из списка открытых; штатного Undo пока нет | Отдельный будущий патч: отмена последней успешной отметки с проверкой текущего Markdown, без перезаписи внешних изменений |
| P2 | Не все icon-only действия явно названы для доступности | В ветках чата/задач: подписи очистки, копирования и обновления; полный аудит VoiceOver ещё нужен |
| P2 | Пользователь не всегда понимает охват истории статусов и полного архива | Рассмотреть короткое пояснение охвата поиска/архива, проверив реальные данные в MeetingRepository; не обещать полный архив по ограниченному status-feed |

P1/P2 здесь обозначают порядок работ, не CVSS и не результат исследования
частоты отказов. Риск обрезания элементов следует из размеров в коде;
точную геометрию надо подтвердить на Mac.

## Что уже сделано правильно

Первый запуск уже собирает имя и папку памяти, проверяет готовность и
помогает с моделями. Обработка использует реальные стадии и номер части
обновления графа. Есть повтор после ошибки, сохранение исходника,
предупреждения о деградации и переходы из источников к встрече/файлу.
Слабые совпадения поиска не превращаются в чипы опоры ответа. Это полезные
механизмы; их следует проверить сквозным сценарием, а не заменить общим
спиннером или ещё одним самостоятельным мастером.

## Предлагаемый пользовательский путь

1. **Первое открытие:** один понятный следующий шаг — подготовить запись.
   Дополнительные модели и календарь показывать по контексту; обязательные
   условия и необязательные возможности не смешивать.
2. **Перед записью:** видно, готовы ли микрофон и системный звук. При
   ограничении — действие исправления и ясное описание, какая часть
   разговора будет записана.
3. **Запись:** таймер, источник звука, Стоп. Подсказки и облачные слои
   остаются вторичными по отношению к сохранности записи.
4. **После Стоп:** стадия по факту, подтверждение сохранности исходника,
   возможность продолжить другую работу. Процент — только при измерении.
5. **Результат:** сначала главное, решения и поручения; глубины документа
   открываются по необходимости, без обязательного чтения стенограммы.
6. **Вопрос к памяти:** понятна выбранная модель, включена ли память,
   какие материалы переданы и где выполнялась генерация. Отсутствие
   релевантных материалов не маскируется уверенным ответом.

## Почему пока не добавлять библиотеки и новый агентный слой

Для текущих исправлений достаточно SwiftUI: ViewThatFits, адаптивных
контейнеров, системного alert и accessibilityLabel. Новая зависимость
не исправит принятие/отклонение отправки и не сделает чипы доказательством
ответа. Внешний мониторинг также не требуется для этих изменений.

Для проверки ИИ полезнее сначала собрать обезличенный набор задач:
найти решение по встрече, сравнить две даты, найти противоречие, ответить
при отсутствии данных. После этого можно сравнивать эмбеддер, reranker
или NLI по качеству извлечения и проверяемости ответа. NLI не следует
представлять пользователю как гарантию истины; это отдельный компонент
проверки, качество которого надо измерить на русском материале.

## Проверка результата

Автоматически в ветке чата: отказ отправки во время генерации и для пустого
вопроса не меняет сообщения/историю и не запускает сеть; удалённая мета
не помечена как локальная. Тесты используют временную историю вместо
пользовательского каталога. Сборку и прогоны выполняет macOS CI.

Ручной прогон: RU/EN/ZH; светлая/тёмная тема; окно 900/1180/1440 pt;
drawer 430 pt; отсутствие Ollama; отказ отправки; отмена/подтверждение
очистки; локальный и явно разрешённый удалённый адрес; чтение старого
ответа во время генерации; Tab и VoiceOver. Проверять не только
видимость, но и совпадение видимых кнопок с кликабельными областями.

Для проверки удобства провести сравнение старой и новой сборок на одной
серии задач: первая запись, найти решение вчерашней встречи, отметить
поручение, отменить ошибочное действие, спросить о нескольких встречах,
восстановиться после отказа модели. Замерять завершение без помощи,
время до результата, ошибочные действия и потерянный ввод. Порядок
сборок чередовать, чтобы обучение не выдавало себя за улучшение.
Целевые значения назначить после базового замера; этот отчёт не
содержит выдуманного процента улучшения.
