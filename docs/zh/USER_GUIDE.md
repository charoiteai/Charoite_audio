# 用户实用指南

*[English](../USER_GUIDE.md) · [Русский](../ru/USER_GUIDE.md) · **中文***

这不是功能清单——完整功能见[《功能》](FEATURES.md)。本指南按日常流程说明：
准备 Charoite、录制会议、看懂会后处理、取得结果，以及在失败后安全恢复。

## 第一次正式会议之前

1. 完成[安装](SETUP.md)。使用预编译应用时，首次运行向导会询问你的姓名和图谱
   文件夹——无需手动编辑 `config/config.yaml`。从源码运行时，请填写
   `sufler.user_name` 与 `sufler.graph_dir`。
2. 也在那里检查就绪状态：Python 运行环境、配置、模型地址、Ollama、模型、麦克风
   和图谱文件夹。从源码工作时，请在**设置 → 连接 → 数据文件夹**中指向仓库文件夹；
   其下的开关「从此文件夹运行守护进程代码（开发）」决定应用运行那里的代码，
   还是自己已签名应用包内的那份。
3. 线上通话无需任何配置：首次录制时 macOS 会请求「屏幕与系统音频录制」权限，
   点击「允许」，然后重启 Charoite。没有它只能录到您的麦克风。BlackHole 只在
   权限被拒绝、或不经应用直接在终端运行时作为备用方案。
4. 先做一段短测试录音，并等到结果卡片出现。这一次会同时验证声音采集、
   识别、Ollama 和图谱写入。

如果就绪检查没有解释问题，请在仓库根目录运行：

```bash
python3 scripts/doctor.py
```

`doctor` 不只检查安装，还会实际测试模型生成、未完成会议、导入队列和磁盘
空间。它只报告，不会自行修改任何内容。它读取 `CHAROITE_ROOT` 指明的数据文件夹；
检查预编译应用的数据见[《安装》→ 诊断](SETUP.md)。

## 每场会议之前

- 菜单栏应显示**“可以录音”**（上一场处理完后为**“会议已就绪”**），而不是
  “Ollama 无响应”之类的问题提示；出现问题时菜单栏图标还会变黄，只有数据正在
  丢失时才会变红。
- 音源由 Charoite 自行选择并在开始后显示：「系统音频（ScreenCaptureKit）」
  为常规路径，「BlackHole」为备用。无需切换系统输出设备。
- 告知参会者正在录音。Charoite 不会让机器人加入会议，也无法代替你完成告知。
- 启用日历集成后，应用会询问是否开始录音，但绝不会自动开启录音。

## 会议进行时

在主窗口「会议」栏按**“聆听会议”**（`⌘⇧Space`），或在菜单栏按**“开始录音”**。
红点与不断增加的计时器表示会话正在运行。

不要只看计时器，也要检查最初几行逐字稿：

- 麦克风声道应标成配置中的你的姓名；
- 对方应出现在另一个声道，或显示为“说话人 N”；
- 如果没有系统声音，必须当场修复——事后无法只从麦克风恢复对方声音；
- 如果出现“磁盘录音已关闭”，实时逐字稿仍会继续，但失去了用于精确重建的
  保险音频；
- 如果开始录音时剩余空间不到约 880 MB，警告（«МАЛО МЕСТА НА ДИСКЕ: …»，
  即“磁盘空间不足”）会留在整个会议期间，而录音仍在继续。请腾出空间：
  若磁盘随后写满，丢掉的是会议的后半段。阈值是
  `audio.record_free_min_bytes`（字节）。空间检查失败只在守护进程日志里
  记一行，不会停止录音；
- 临界内存压力（«ПАМЯТЬ НА ИСХОДЕ: …»，即“内存见底”）会留在屏幕上，直到
  机器重新宽裕。轻微警告只出现在守护进程日志里：本机驻留着本地模型时，
  这是正常背景；
- “提示落后：丢失最多 N 秒实时音频”这一行表示识别跟不上谈话，实时逐字稿漏掉了
  部分语音。只要磁盘录音仍在进行，会议本身是安全的：最终逐字稿会从音频重建，
  内容完整——受影响的只是会议中的提示。如果同一行说录音没有在进行，这段音频就
  永久丢失了，必须立即处理：释放磁盘空间、关闭占用资源的应用。落后通常意味着
  机器很忙——内存里驻留着另一个模型、正在构建或导出视频。

只要问题仍存在，警告会持续显示在会议窗口和菜单栏中；普通的提示或会议纪要
消息不会将其清除。“STT 无响应”表示转写停在所标出的阶段；达到 100 秒后，
现有 watchdog 会尝试恢复录音。红色“音频未写入磁盘”优先于其他状态；唯一会
替代它显示的，是守护进程自身带有具体原因的错误信息（«ЗАПИСЬ НА ДИСК ВЫКЛЮЧЕНА: …»，
即“磁盘录音已关闭：…”）。故障通道的录音在本次
会议结束前不会恢复——从那一刻起该通道不再有可用于恢复的原始音频；其余通道
和收尾处理继续工作，释放的磁盘空间正是为它们所需。

主窗口可以关闭，状态仍留在菜单栏。录音中退出应用会要求确认，因为退出会
停止本次会议。

忘记停止并不可怕：录音会自行结束——若从头到尾无人说话，5 分钟后停止；
交谈结束后陷入沉默，15 分钟后停止；无论如何 6 小时后停止。还有第四种情况：
若整场录音都没听到对方的声音——系统声道一直安静，只有您在说——沉默按 10
分钟计算，而不是 15 分钟。请注意，线下会议在我们看来是一样的：所有人同处
一室，声音都进入麦克风，也就是说「对方」按定义并不存在。如果您的会议以线
下为主，请设置 `alone_minutes: 15`，该规则便不再改变任何行为；设为 `0`
则完全关闭。还有第五种情况——告别语：听到「大家再见」「回聊」时，
录音只等一分钟静音而不是十五分钟（预警立即出现，任何一句话都会取消）；
连续两次告别——互道再见——则立即停止录音。句子中间的「再见」不算数；
`farewell_seconds: 0` 可关闭该规则。结束前一分钟
会出现预告（状态栏；若窗口不可见还会有横幅通知）——说句话录音就会继续。
停止走的是与「停止」按钮相同的常规路径：会议被保存并处理，不会丢失任何
东西，状态栏还会保留停止原因。自动停止管不了的情况：房间里开着的电视或
音乐——那些人声对我们就是交谈，这类录音只能靠 6 小时上限终止。阈值配置见
`config/config.yaml` 的 `sufler.autostop`。

## 按下“停止”之后

处理过程独立于窗口。应用读取流水线的真实状态，不会编造百分比。逐字稿、纪要、会议提示、归档中的纪要和导入的会议在写入时已经去掉本机路径：主目录换成 `~`，主目录之外的数据根换成 `‹данные Чароита›`。目录名只由字母、数字、`_`、`-` 以及名字内部的点延续。用来恢复手改的那份隐藏的上一代副本保持原样。日志不改写。

| 状态 | 含义 | 该怎么做 |
|---|---|---|
| 正在保存录音 | 声道正在完成写入；必要时把遗留 PCM 转为 WAV | 不要移动 `recordings/` 中的文件 |
| 正在重建逐字稿 | 完整录音重新识别并做说话人分离 | 可以关窗口，但不要让 Mac 关机 |
| 正在更新图谱，第 N/M 部分 | 正在生成纪要、节点、链接、归档与摘要 | 部分编号应继续前进 |
| 会议已就绪 | 图谱笔记与结果卡片已经发布 | 打开卡片或 Obsidian |
| 失败——原始文件已保留 | 流水线没有生成完整图谱结果 | 打开逐字稿并重试 |

处理时长取决于会议长度和模型。成功处理几场之后，Charoite 会按你过去运行的
中位数给出估计。状态 30 分钟未更新时，应用会显示失败，而不是永远转圈。

## 会议结果卡片

卡片直接显示最常用的结果：

- 主题、日期，以及根据逐字稿时间戳估算的时长；
- 从逐字稿中识别到的参会者；
- 就地切换的四种阅读深度——摘要 · 纪要 · 分析 · 逐字稿；卡片会记住你上次读的那一种；
- `Саммари.md` 中的概要、决策和行动项，并可跳转到本场会议的任务；
- 当前深度的**“在编辑器中打开”**；**“更多”**里有 Obsidian、“复制参会者纪要”、
  复制摘要/任务/全部，以及**“重建结果”**：手工修改过的逐字稿保持不变，纪要按它
  重建；未改动的逐字稿在录音仍保留时重新识别（旧版本存入 `transcripts/.prev`）。

标题旁的铅笔会协同重命名逐字稿、归档文件夹、图谱笔记和状态里保存的路径。
不要在 Finder 中分别重命名这些部分，否则容易留下失效链接。**“忘记会议…”**会先
列出将要删除的全部痕迹——逐字稿、录音、归档文件夹、图谱笔记、核心中的提及——
只有在按下“永久删除”后才会删除。

给参会者发送内容时，请使用清理后的会议协议，而不是原始逐字稿：

```bash
.venv/bin/python scripts/protocol.py --style plain --copy
```

默认选择最新会议，也可传入日期或标题片段。协议包含概要、决策、行动项、开放
问题和风险；无论使用什么参数，都不会包含原始逐字稿——卡片里的“复制参会者纪要”
也一样。

## “近期会议”不是完整归档

**「会议记录」**栏（菜单栏的**“近期会议”**也会打开它）最多显示最近 14 天的 20 条
处理状态（今天 · 本周 · 更早），用于回答“昨天那段录音后来怎样了”，并不替代
图谱归档。列表上方的搜索框走得更远：它搜索整个归档中的摘要、纪要和复盘，
点中结果时，若该会议在列表中则打开会议卡片，否则直接打开文档本身。

完整历史仍位于 `<graph_dir>/Встречи-архив/` 与 `Встречи/`。状态从列表过期
不会删除会议文档。全部存储位置和保留规则见
[《数据与恢复》](DATA_AND_RECOVERY.md)。

## 处理没有完成时

按从最安全到更手动的顺序操作：

1. 打开错误状态提供的逐字稿。如果其中有对话，重试所需的源数据仍在。
2. 在会议上按**“重试处理”**（或菜单栏的**“重试”**）。重试进行时，第二次启动会被阻止。
3. 若重试没有开始，运行 `python3 scripts/doctor.py`。常见情况是 Ollama 能列出
   模型，但生成请求本身已经卡住。
4. 按提示重启 Ollama，再从应用中重试。
5. 若状态记录已消失、逐字稿仍在，手动运行：

```bash
CHAROITE_ROOT="$PWD" .venv/bin/python src/rebuild_transcript.py transcripts/<文件>.md
```

会议就绪前不要删除逐字稿或 `recordings/` 中的新文件。重试从逐字稿开始，
而录音能让重建更加准确。

## 旧录音与手机录音

音频、已有文本或 Zoom/Teams 字幕都能进入同一条流水线：

```bash
CHAROITE_ROOT="$PWD" .venv/bin/python scripts/import_meeting.py recording.m4a --date 2026-07-15
CHAROITE_ROOT="$PWD" .venv/bin/python scripts/import_meeting.py zoom.vtt --title "规划会议"
```

会议日期取自录音本身（容器元数据或手机文件名中的时间戳），否则取文件时间；
`--date` 和 `--time` 可覆盖。同一个文件导入两次会被识别为重复，不再重新处理。

在应用中，把文件拖到**「外部录音」**标签页，或在**设置 → 录音导入**中指定监视
文件夹（m4a/wav/mp3、txt/md、vtt/srt）：放进去的文件会自动成为会议。该标签页显示
队列、带**“重试”**按钮的失败文件，以及每个副本的删除日期。正在增长的 WAV 会等复制
完成后才处理。iPhone 伴侣应用把录音投递到同一个文件夹；iPhone 自带「语音备忘录」
的录音也可以接入（需主动开启 `audio.voice_memos_bridge`，并授予完全磁盘访问——
见[安装](SETUP.md)）。

拖到标签页的原件留在原处。`done/` 中已处理的副本以及会议归档中的音频源，会在导入后
`audio.import_keep_days` 天（默认 2 天）删除——与 `record_keep_days` 无关；失败的
文件永远不会被删除。备份和删除时要记住这一点。

## 会议之间

- **记忆**根据过去的会议作答：与本地模型对话，开启**“图谱记忆”**时回答依据会议、
  图谱节点与档案；回答下方的标签显示混入了哪些来源。“⚠ 图谱匹配较弱”表示档案里
  可能没有答案。快速提问也可以直接写在菜单栏的输入框里。
- **任务**汇总未完成的 Markdown 复选框——你的排在最前，可按会议或按期限查看；
  勾选后直接写回图谱文件。
- **听写**、**语音笔记**和**日记**可从菜单栏通过 `⌥⌘D`、`⌥⌘N`、
  `⌥⌘J` 使用。

最短的日常闭环是：确认绿色就绪 → 开始录音 → 确认双方声音都出现 → 停止 →
等待卡片 → 分享决策和行动项 → 必要时修正标题。
