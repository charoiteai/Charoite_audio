# Charoite 如何维护

*[English](../../MAINTENANCE.md) · [Русский](../ru/MAINTENANCE.md) · **中文***

Charoite 由 AI 在人类指导下维护。本页描述的是真实运转的流程——证据是
提交历史，而不是一场表演。

## 角色

- **人类所有者**设定方向与优先级，制定下述规则，决定何时发布什么，
  负责隐私政策，并对结果负责。
- **AI 维护者**（Claude Code，以 `charoiteai` 身份提交）编写代码：
  设计、实现、测试、文档、发布——完整闭环。

## 一次变更如何发布

1. 所有者提出任务和重要约束。
2. Claude 实现它——代码、测试和文档在同一次变更中完成。
3. **独立对抗式评审。**每个实质性变更都由未参与编写的第二个头脑检查：
   独立的 Claude 代理，或完全不同的模型（去相关评审）。发现的问题在
   PR 打开前修复并复查。
4. 本地闸门通过：`scripts/preflight.sh` 运行 lint、布局守卫、隐私标记、
   完整的 Python 测试、应用有改动时的 Swift 应用测试，以及改动行的变异
   检查，并以一行结论收尾。2026-09-27 实测：Python 测试 3936 个，macOS
   应用的 Swift 测试 530 个，iOS 测试 67 个，Android 测试 28 个。
5. Pull request 运行 CI：`lint` 与 `pytest (src/)`（含布局门禁）为必需；
   CodeQL、改动行的变异检查、供应链检查（zizmor、dependency review）、
   文档守卫、约定式 PR 标题、匿名化闸门，以及在相应代码改动时的 Swift、
   iOS 与 Android 构建一同报告（[RELEASING](RELEASING.md) 解释了为什么只有
   两项会阻止合并）。
6. 必需检查为红则禁止合并；参考性检查为红，合并前要读，而不是放过。
   CI 全绿则 squash 合并；release-please 切出带版本的发布，每个发布在
   所有者签署其更新清单之前保持 pre-release。

### 守卫不许被噤声

变红的守卫陈述的是关于代码树的一个事实，维护者的工作是改变这个事实，
而不是改变守卫。由此得出三条规则，它们对 AI 维护者和对任何人一样有
约束力：

- 失败的检查永远不能靠重新生成它所比对的工件、扩大规则的作用范围，
  或在没有卡片和书面理由的情况下声明例外来变绿。
- 例外是一项决定，所以要写在评审者会读到的地方——写在工件里、紧挨着
  它所豁免的东西，并用平实的话写明理由。
- 这些理由中的数字来自测量，而不是记忆。手敲的计数在写下的第二天就会
  与代码脱节，而仓库里没有任何东西能发现这一点。

自主的夜间运行确实存在且属常态——它们经过与白天工作相同的评审和 CI
闸门。无论何时，红色流水线上不合并任何东西。

## 流程本身的隐私

产品的承诺——一切不离开你的机器——同样适用于它的构建方式：

- **pre-commit 匿名化闸门**（`scripts/check_private_markers.py`）
  阻止姓名、雇主、内部系统名称和逐字稿片段进入公共仓库；CI 中按格式
  匹配的第二道防线对来自 fork 的 PR 同样生效。
- 当使用外部模型做去相关评审时，它只能看到**公共树的干净 checkout**
  ——绝不接触用户数据，绝不接触 gitignored 的本地状态（录音、逐字稿、
  配置）。
- 密钥和令牌存放在仓库之外；为更新清单签名的私钥永远不进 CI。

## 对贡献者意味着什么

欢迎外部贡献，评审走同一条流水线——见 [CONTRIBUTING](CONTRIBUTING.md)。
安全报告通过 [SECURITY](SECURITY.md) 提交；阅读它们的是所有者，而不只是
AI。
