# 架构

*[English](../ARCHITECTURE.md) · [Русский](../ru/ARCHITECTURE.md) · **中文***

## 概览

```
mic ───────┐                        ┌─ live transcript (per-voice paragraphs)
           ├─ AudioHub ─ STT ─ daemon ┼─ loops: ⚡ answers · theses · minutes
system audio ┘  (3s chunks)         │   · déjà vu · names · dialogue markup
（ScreenCaptureKit；BlackHole 为备用路径）
                                    └─ NDJSON stdout ←→ stdin commands (UI)

Stop → recording rebuild → graph update → archive + Summary → [Claude debrief]
```

一切都在你自己的机器上运行；流水线的网络调用仅指向 localhost（Ollama）。
云端层是一个独立的、默认关闭的选项；应用自己发出的唯一请求——向 GitHub
检查新版本——见下文「应用何时得知新版本」。

## 守护进程（src/daemon.py）

单个进程，多个线程循环围绕一个共享加锁的 `Transcript` 运转：STT 循环、
快速问题触发、即时回答、自动提示、共同思考（要点）、会议线程、实时会议纪要、
基于核心（Cores）的既视感（déjà vu）、人名解析、对话标注、实时档案上下文
（按当前会议主题检索图谱）、自动停止、云端循环、心跳。事件以行式 JSON 流向
stdout（`{"type": "transcript"|"thesis"|"hint"|…}`）；命令从 stdin 传入
（`hint`、`ask <question>`、`expand [主题]`、`cloud`、`summary`、
`set hints|theses|cloud on|off [quiet]`、`stop`）。任何 UI 都可以架在这套
协议之上；第二个实例会被 flock 阻止。
`Transcript` 位于轻依赖的 `src/transcript.py`；运行时模块不再导入旧入口 `main.py`。

守护进程的状态带有故障标志（`{"type": "status", "error": true}`）：应用把
这类状态显示为错误，普通状态则清除标志。模型故障不会变成提示文本——只会
变成状态——因此屏幕上保留最后一次成功的提示。

**音频从哪里来。** 系统音频由应用通过 ScreenCaptureKit 采集，写入一个不断
增长的流文件，由清单 `data/sck_stream.json` 描述；从 macOS 15 起麦克风也经
同一条流到达，完全不打开 PortAudio。`AudioHub` 像 `tail -f` 一样读取这条流。
没有新鲜的清单时，hub 走备用路径：BlackHole（需手动安装的驱动）加上经
PortAudio 的麦克风。没有第三条路径：Core Audio tap 流已于 02.09 移除——它的
聚合设备在 06–07.08 四次让 CoreAudio 挂起，而 ScreenCaptureKit 不创建聚合设备。
两个声道分开保存，这就免费得到了「我/他们」的说话人分离；两个声道同时有语音
时，麦克风的音频块作为扬声器回声被丢弃。

### 声道标签与所有者——同一个来源（src/channel_labels.py）

谁在对着麦克风说话、谁是会议的所有者，守护进程和采集都去问同一个
`ChannelLabels` 对象，它由配置一次性构建：声道的原始标签（`mic_raw`，
「Я」或姓名，除非姓名与中性标签冲突——`mic_label_for` 规则与 `AudioHub`
共用）、所有者的署名（`mic_signed`：姓名；姓名为空时为「Я」；冲突时为空）以及
用于逐词比对的姓名。在第 1 阶段之前这是三个来源，而且会分歧：姓名设为
「Собеседник 2」时，麦克风音频块在语音计数里算麦克风，在署名里却算外人
（30.08 审计）。批次 D-П2。

### 正在进行的会议优先于后台（src/live_gate.py）

本地模型只有一个，想用它的却有好几个：重建早前的录音、图谱抽取、夜间
循环——还有正在进行的会议。带 MLX 运行器的 Ollama 在模型忙碌时不排队，
而是在四分之一秒内返回 `503`；没有保护时，重建一段 18 小时的录音
（18.08）让一场会议 45 分钟没有提示。三条规则：

- **「会议进行中」= 守护进程锁** `logs/daemon.lock`：守护进程的寿命恰好等于
  录音时长。后台工作（`graph_updater`、`rebuild_transcript`、夜间的
  `wait_for_idle`/档案）用非阻塞 `flock` 检测它，锁被持有时就等待——
  长抽取的分块之间也一样。重建可以无限期等待（整体等待，包括 STT 和
  说话人分离）；夜间循环有上限（早晨的会议不能吃掉整个夜晚）。每台机器
  同一时刻只运行一个重建（`logs/rebuild.lock`）：被门放行的孤儿录音和
  「停止」后的新录音不会同时启动。在已占到的队列内部，重建的模型调用（说话人
  姓名、纪要）为实时会议最多等待 10 分钟，之后在拥挤中运行并记一行日志：在这里
  无限等待会让整个队列为别人的会议停摆。「会议进行中」仅指 `flock` 因他人持锁而
  诚实地拒绝；文件缺失、无权限或卷不支持 `flock` 都不会让后台停滞。
  第二个信号——本机上的守护进程，无论其数据根目录——是
  `live_gate.daemon_process`：MCP 状态与占位节点迁移共用同一个模式
  （`python` 且脚本是第一个参数），因此打开了 `src/daemon.py` 的编辑器
  不算守护进程。
- **忙碌 ≠ 挂掉。** `llm.stream`/`complete` 在调用方的预算内以递增的
  间隔重试 `503/429/502`（实时循环最多 30 秒，图谱抽取最多 10 分钟）；
  `llm_health.probe` 区分 `BUSY`，绝不在别人的生成过程中重启服务器。
- **自己的生成正在进行——是事实，不是猜测。** 每次向本地模型发请求期间，
  传输层（`llm._open_stream`、`llm._post_busy`）都持有一个 `flock` 锁定的
  租约文件 `data/llm_inflight/<pid>-<id>.json`（`model_lease`）：进程一死，
  内核立刻释放，无需 pid 或 mtime 推断。文件按调用而非按进程建立：守护进程
  会在同一个 pid 里并行多个生成。存活只有一个判据 `deadline` = 最后一次确认
  存活的时刻加上停滞阈值，阈值由同一请求的读超时推出（传输层自己会中断超过
  超时的沉默，阈值略高于它，否则活着的文档预填充会被当成挂起）；流式请求中
  带数据的行会推进 deadline，`: keepalive` 注释不会。文件协议属于写入方：
  租约绝不会在没有锁的情况下可见，也绝不原地改写——每次发布都是一个新的、
  已加锁的 inode 重命名覆盖到该文件名；读取方只凭锁判断存活（有锁但读不出
  内容也算活着），不删除孤儿（由下一个写入方清理）。重启前 `llm_health`
  读取指向该服务器的租约：有存活且未停滞的租约，说明服务器正忙于我们的工作，
  调用方排队等它；租约停滞或不存在，则照旧重启；传感器不可读则记一行日志——
  若它从未工作过则照旧重启，若曾工作后失效则一直保持不重启，直到手动重启。
  保护写在 `_restart*` 自身，并连同禁止触碰非 loopback 地址的规则一起，任何
  通往 kill 的路径都继承二者；越过存活租约的手动紧急重启是
  `scripts/doctor.py --restart-llm`，成功以探测得到应答为准。指向云端网关的
  租约不会阻止本地重启（按服务器地址匹配）；在忙碌队列中等待不持有租约——
  队列会自愈。
- **流内部的错误就是错误。** 200 响应中出现的 `{"error": …}` 行，或没有
  终止符就结束的流，都会抛出异常：被截断的纪要绝不会被当作完整的。

### 提示优先于线程（守护进程内部）

自 30.08 起，对话标注也受仲裁器管辖：它曾是唯一绕过锁使用模型的循环——每六秒
900 个 token，提示与 ⚡ 排在它后面；现在它安静地尝试取锁一秒，取不到就让这段
稍后再标，手动提问甚至能在生成中途打断标注。快速触发器丢掉的帧会被计数，每分钟
一次以错误状态报告，而不是悄悄消失。

在外部，争夺模型的是各个进程；在守护进程内部，是它自己的循环。26.08 事故：
自动要点循环（「线程」）在实时配置下跑主力 35b 模型并占住 Ollama 连接——门是空的、
会议在进行，提示却从内部被饿死。事后复盘定下的规则：

- **后台不用大模型。** 线程严格运行在 `llm.small` 上，不在主模型上重试：一块 GPU
  上的两路生成会掐住提示引擎。若未配置 `llm.small_model`，守护进程启动时在 err
  日志里写一行说明——禁止悄悄退回主模型。
- **几乎零等待的槽位。** 线程以 1 秒超时去取提示槽：忙则跳过这一拍，而不是排在
  提示前面。连续四次落空后，它以 20 秒等待尝试一次（突发），免得在密集的会议上
  永远饿死；突发失败按普通落空计。
- **没有死循环。** deep_loop 已删除：应用自 #394 起发送 `set theses off quiet`，
  这个循环在任何一次实时会话中都没有运行过——「看似在做事」的代码比没有更糟。

### 决策门在影子模式下观察（src/decision_gate.py）

今天 ⚡ 的问题由结构性检查挑选（`question_filter`：开头有「?」或疑问词，再看
长度与重复）。通过的一切都会唤醒模型；模型找不到问题时回答「请澄清」——这种
拒绝不会进入线程，但模型的秒数（开启云端时还有配额）已经花掉了。项目规则不允许
用短语清单来治，而每句话一个 LLM 裁判的开销与回答本身相当。

决策门一遍前向、不做生成就回答「这是不是问题」，并给出置信度；设想是级联：门
只在确信时替模型保持沉默，其余照旧交给模型。后端按偏好顺序：`models/decision/question_gate/`
中训练好的头（`model.onnx`、`tokenizer.json`、带校准温度的 `labels.json`），或借助
`models/nli/` 中已有的 NLI 模型做 zero-shot（两个假设；不需要新包，但置信度未校准）。
两者都没有时，工厂以一行说明拒绝，守护进程照旧工作。

目前门不做任何决定。唯一的模式是影子（`sufler.decision_gate_shadow: true`，默认
关闭）：裁决与 ⚡ 的生成并行计算——⚡ 不等它——一行 `gate-shadow:` 连同结果
（`answered`、`refusal`、`failed`）写进 err 日志。行里没有任何内容：标签、置信度、
延迟。同一时刻只有一次运行在进行；上一个问题还在裁决时到来的问题得到
`reason=busy`，超过 45 秒则为 `hung:<时长>`，因此卡住的裁决器会在测量中显现，
而不是悄悄堆积线程。是否真正启用门、用什么阈值，由 `scripts/gate_bench.py` 依据
累积的行（以及人工标注的数据集）决定，而不是凭猜测。

### 应用里什么在重绘

本地模型和录音与界面本身共享这台机器，因此 UI 有自己的资源契约。24.08 实测：
应用在 4.5 天的运行时间里平均占用 37% CPU——没有一帧动画，纯粹来自多余的重绘。
复盘得出两条规则：

- **跳动的值住在自己的视图里。** 录音时钟的秒数是 `RecordingClock`（由开始时间
  驱动的 `TimelineView`），而不是服务里的 `@Published`：每秒发布一次会让带十个
  订阅者的整个今日屏幕在整场会议中不停重绘。时长由开始时间推导，因此休眠的笔记本
  不会「吃掉」它，不可见的视图也根本不跳动。
- **发布门比较消费者读取的东西。** 每两秒一次的处理状态轮询发布相同的值，白白
  唤醒订阅者——相等门是必需的。但只比较原始快照还不够：「处理中」会因「时间」
  （三十分钟无动静）变成「错误」，而文件毫无变化。门比较的是解析后的状态——否则
  挂住的流水线会悄悄变成永远转圈、没有「重试」按钮的状态（两个案例都来自 #433 的
  DeepSeek 评审轮：先在会议卡片上，后在错误标记上）。

### 云端层：每个循环付出什么

五个循环通过无头 CLI 调用云端：会议中的即时回答与线程修订、会后审阅、夜间档案
修订和夜间核心修订。它们的共同规则放在 `src/cloud.py`（每一步的模型与投入度、
调用隔离、代理）；许可由 `src/privacy.py` 发放。26.08 的审计（两位独立评审）
确认了框架并封住四条接缝：

- **CLI 错误不是回答。** 实时循环取 stdout，为空时用 stderr 顶替：「Unknown model」
  和「403」作为云端回答进了会议画布和审计记录。现在检查返回码，失败作为错误进入
  状态，绝不进入审计。
- **工作进程不再无声死亡。** 缺少 `claude` 时抛出的 ENOENT 越过了 `finally`：图谱
  快照成了孤儿，日志停在第一行，会议就这样没有审阅。现在这是一条普通的失败路径，
  并记下原因。
- **所有写图谱的人共用一把锁。** `cloud.lock` 原先只有会议审阅会拿；夜间档案修订
  不拿锁就改同样的文件，邻居的边界检查把它的修改送进隔离区，而运行却报告「✓ 已应用」。
  锁移到 `src/file_locks.py` 并共用。
- **禁止读取符号链接。** 符号链接的目标在图谱之外，而 `Read(/**)` 在字面上覆盖它。
  实际运行表明 CLI 会自行解析路径并拒绝向外读取——但只读模式根本没有 deny 规则，
  边界完全依赖一个外部程序的行为。

### 图谱节点绝不会在写到一半时丢失

`write_text` 以写入方式打开文件，在写下任何内容「之前」就把它截断为零。卷满了、
iCloud 配额用尽（图谱就在那里）、夜间运行在写入中途被杀——积累了一年的核心就变成
一个 0 字节的文件。无处可恢复：这是唯一的副本。

所有写入图谱的操作都经过 `safe_write.write_text`（`src/charoite_graph/safe_write.py`）
——先写目标旁边的临时文件，再 `replace`。「所有」指 `graph_updater`（节点、MOC、
会议笔记、复盘）、`tier3` 中的核心合并以及 `rebuild_transcript` 中的最终逐字稿；
唯一有意的例外是锁的 PID 文件，那里创建文件本身就是目的。在 POSIX 上这在同一卷内
是原子的：读者要么看到完整的旧版本，要么看到完整的新版本。临时文件就放在目标旁边
而不是 `/tmp`：跨卷移动从来不是原子的。文件名带 PID，因此两个进程不会交错拼出同一个
文件——最后替换的一方胜出，但是完整的。符号链接会被解引用：图谱里的共享笔记有时是
链接，用普通文件替换链接本身是错的。权限和扩展属性（Finder 标签、Spotlight 注释）
转移到新 inode 上，权限用显式 `chmod`——否则节点在第一次修改后就会丢掉手动设置的
权限。时间「不」转移：夜间按 mtime 挑选工作（`tier3` 取比上次运行更新的核心），
今天更新、但一周前首次写入的节点会掉出增量。显式 `chmod` 的原因是只差一个字母的
`copystat` 会连带时间，因此「不碰时间」的意图写在代码行里而不是隐含着。需要来源
时间的调用方——归档中的纪要正本——显式传入（`times=`）。同一个函数还持有丢失更新
的门：`expect` 是读取源文件之前拍下的 stat 快照，期间变过的文件不会被覆盖。

这个模式项目里早就有，但被手工复制在五个地方（逐字稿、纪要、档案、遗忘会议、wav），
而十几处写图谱节点的地方没有它——0.62.0 版本的审计正是发现了这一点。现在只有一份
供所有人使用：并排的副本会渐行渐远，一个有 `finally`，另一个没有。

### 云端修改的是图谱副本，而不是图谱

云端审阅在「沙箱」里工作——运行前刚拍下的第二份图谱副本。CLI 的工作目录指向那里，
`--permission-mode dontAsk` 下的 `Edit(/**)` 被绑定在它上面：越出目录的写入由 CLI
自己拒绝（实验验证过——请求目录外的文件返回「无权访问工作目录之外」）。与此同时，
流水线继续写真正的图谱：下一场会议的抽取、纪要尾部、基于核心的既视感。

由此得到主要性质：**作者身份由构造得知。** 沙箱与快照的一切差异都是云端做的；其余
一切属于别人，对转移完全不可见。这取代了六个「自己的文件」的标志（名字中的会议
时间戳、transcripts 里的原件、写入者签名、流水线的时间窗口、隐藏路径、可执行性），
其中每一个都在某个边缘情况上招来一个 Critical，围绕它们进行了十六轮评审。

转移在图谱锁下进行，并逐个文件决定：

- 允许位置的修改——写入图谱；
- 禁止的位置（受保护的文件夹、隐藏路径、作者小节）——进隔离区，不进图谱；
- 窗口期内被流水线改过的文件——保持原样，云端版本进隔离区：实时工作优先。这正是
  旧方案残留的风险：回滚会把纪要尾部连同云端修改一起带走；
- 删除——根本不转移。云端没有理由删节点，而「恢复被删除的」正是 27.08 把 10:32 的
  会议笔记连同 11:33 会议的五个产物一起带走的那次回滚。

无效的回答（超时、残片、非零退出码）不需要回滚：图谱一个字节都没变，沙箱直接丢弃。
它的修改进隔离区——人仍然可以看看云端做了什么。

APFS 上的两份图谱副本几乎免费，这是测出来的而不是宣称的：在实际图谱上（6071 个
文件、194 MB），每份副本耗时 1.8 秒，占用 1.5–3.5 MB 实际块——`clonefile` 与原件
共享块，直到有人写入。与审阅运行的半小时相比，这不值一提。注意：守护进程的数据在
另一个卷上时 `clonefile` 不起作用（EXDEV），副本就成了实打实的 194 MB 读写——可察觉
但可以忍受；在同一卷上（标准安装即如此）代价为零。快照保持独立、不被触碰——源文本
对照它核对，流水线的修改也靠它发现。

### 遥测回答「为什么」

接连两次诊断都撞上同一堵墙：数字回答不了主要问题。

**STT。** 「transcription_ms=3225」本身毫无意义：慢模型和大块音频看起来一样。这一行
还带着「整段录音」的累计：调用了模型几次、最短的片段、总体 RTF。「audio_s=6.0」对一次
六秒的调用和十二次半秒的调用描述相同，代价却不同——短片段承担同样的固定开销（27.08
实测：0.3 秒的片段 13.7x，十秒的片段 29x）。

累计按录音而不是按循环计算，这不是小事。`state=lagging` 行只在落后时写出，而落后时
布局切换到 `shed`，每整块只交一个片段——其中按循环的数字会是常数（声道数和块长），
无论流水线在健康循环里是否切分音频。测量会恰好放在被测现象按构造不可能出现的地方。
循环统计经过模型的音频秒数，落后行带有 `audio_s`、`rtf` 和时间戳——没有时间戳，平静
的机器和负载下的机器无法区分。gigaam-v3 在这台机器上的额定值是 28×（0.63 秒处理
17.6 秒音频，16.07 实测），27.08 的测量予以确认：同一模型在流水线之外为 29×。所以现场
RTF 接近 1 不是模型退化，而是外围开销：把片段切成半秒的段落会降到 13×，单个
onnxruntime 线程降到 6×，其余被第二个声道和重叠吃掉。后台 QoS 另当别论：在 E 核上
同样的工作 RTF 为 0.37，慢七十倍，所以不能出于对邻居的礼貌把转写放到「后台」。逐字稿
只在同一声道的相邻音频块之间核对重叠接缝（0.5 秒）——按采集给出的物理块号而非时钟
（两个语音块之间的静音块、作为回声丢弃的麦克风块也会消耗块号，不会借它们成为邻居）
——并且只在布局中块的开头处核对。接缝只有一个来源：若声道的上一个标签变了（落后 →
健康：声道 → 声音）就用它，否则用自己的；另一个声道或同一块中的第二个声音不这样核对
——别人重复同样的词是话语，不是接缝。

每五分钟日志写入一行 `stt-summary`，无论状态如何。落后行只在队列增长时出现，而平静的
机器上根本不会发生：28.08 连续四场会议没有一次落后，也没有留下任何 STT 数字。否则
只能凭唯一一个糟糕的日子——机器被无关任务占用的那天——来评判流水线。

**提示。** 脉搏用人在状态里看到的同一句话说明沉默的原因：「模型服务器没有响应」、
「模型正忙」。每个出口都记录自己的结果，包括「锁被占用」——这个分支过去无声退出，
脉搏里留着上一次尝试的原因。自动提示与手动提示分开记录遥测：它们在不同线程中运行，
共用的一对会被覆盖。时间拆成 `wait_ms` 和 `model_ms`：提示锁还被线程、纪要、提问的
回答和档案主题占用，等待别人的生成不能看起来像模型慢。

遥测不能拖垮自己的循环：音频计数有保护，状态带默认值读取，故障只留作 stderr 中的一行。

### 夜晚对早晨的承诺

夜间运行（`scripts/nightly.sh`，04:15）在无人使用机器时整理图谱：图谱体检、文件去重、
记忆向量、早间简报、核心修订、档案、云端修订、文件夹索引、第二次体检、简报、记忆基准。
26.08 的审计（两位独立评审）检查了这一区域的承诺并补上缺口：

- **夜晚在夜里结束。** `CHAROITE_NIGHTLY_UNTIL` 上限现在对尾部步骤也可见——去重和
  记忆基准曾越过它，早上还在唤醒模型。等待实时会议的时长也以夜晚剩余时间为上限：过去
  一整小时的等待会把运行拖过上限。文件去重此后挪到了最前面、紧跟体检之后：它只需几秒
  （23.09 在工作图谱上 12.7 秒），而在夜晚末尾它被上限截掉，自 10.09 起连续 12 夜
  （№361）。
- **实时会议优先于夜晚——在最重的步骤上也一样。** 核心对的裁决占用嵌入模型和 NLI
  模型；过去门只设在档案和云端修订上，核心修订一直与实时提词器共用模型。现在它与其他
  步骤一样让路。
- **状态落在人们找它的地方。** 数据根目录在开始时规范化一次：`CHAROITE_ROOT` 中的
  「~」或尾随空格把状态和空闲等待引到一个字面目录，而 python 层看的是真实目录——应用
  根本看不到夜晚。刻意不防第二次「手动」运行：两次尝试（带 pid 的锁目录、经系统
  python3 的 `flock`）都在第一轮评审就招来 Critical，偶尔的重复启动的代价低于夜晚第一行
  上一个脆弱的看守。
- **信号真的能停下它。** `trap` 里没有 `exit`，于是 `kill -TERM` 之后运行继续，「已中断」
  状态被最后的「ok」覆盖——这个状态根本不可达。
- **只有真正干了活才是「ok」。** 一个图谱都没有的夜晚，以及空转的核心修订（没有 NLI
  模型、Ollama 挂了）不再报绿：修订有自己的退出码 2，坏掉的云端 CLI 退出码 3（夜晚在
  状态中标为 failed，rc 不动：脚下的 CLI 更新了，05.09 审计），缺失的图谱在状态里标出。
- **核心修订对每个图谱负责并说出原因。** 只有当每个图谱都被裁决过或无可裁决（单个核心
  不算失败）时该步骤才成功：过去一个图谱通过就够了，主图谱一个月没被修订也无人察觉
  （23.09）。退出码 2 表示某个图谱无法裁决，日志说明原因——嵌入模型的拒绝（附响应码
  与正文）、裁判的拒绝、没起来的 NLI 模型——而不是笼统的「没有 NLI 模型或 Ollama 挂了」。
  退出码 4 表示夜晚上限截断了修订；状态显示「ревизия-ядер(поздно)」，未裁决的核心与已裁决
  的对存放在时间戳旁，下一夜从中断处继续，而不是重新裁决同样的顶部对。给嵌入模型的批次由
  向量之门 `embed_door` 切分（每个请求至多 64 段文本、72 000 个字符）：Ollama 在一个请求
  808 个核心时断开了连接。未裁决核心的列表完整保存。
- **夜晚用 launchd 所用的解释器测试。** 代理运行 `/bin/bash`，在 macOS 上是 3.2，
  在 `set -u` 下展开空数组会让脚本崩溃：一个干净的夜晚被记为失败。测试用的是 PATH 中
  Homebrew 的 bash 5.x，从未看到这一点；`test_nightly_exit` 现在运行 `/bin/bash`。
- **人的修改不会消失。** 在漫长的对裁决期间被改过的核心，不会被内存中的快照覆盖——这一
  对等到下一夜。重复节点手写的「Суть」移入规范核心，而不是只留在轮换的备份里。去重在
  替换前再次核对摘要：在扫描与链接之间被流水线重写过的文件会被跳过。

休眠不是失败：夜间预算按挂钟时间计算，休眠不会让它停下，而 `monotonic` 在休眠中静止——
差值以 `slept_s` 写进 `nightly.json`，只因十分钟以上的休眠而丢掉「(поздно)」步骤的夜晚
以 `slept` 而非 `failed` 结束（30.08：一台休眠笔记本上 04:20 到 09:59 的运行）。完整的
夜晚需要清醒的机器——这是所有者的电源设置；用电池且合上盖子时 `caffeinate` 也无济于事。

### 云端聊天（llm.engine: cloud）

与 Ollama 和 mlx-server 并列的第三个引擎：提示、要点、线程和纪要由外部兼容 OpenAI 的
网关计算，笔记本不再常驻大模型。传输与 mlx-server 相同（`/v1/chat/completions`、SSE）
——只加了一个授权头，因此代码路径共用。

- **两个键才能开启。** `llm.engine: cloud` 说明去哪里，`sufler.cloud_engine: true`
  给出许可。只有其一不够——有地址无许可、有许可无地址，都让本地模型继续工作——而
  `CHAROITE_NO_CLOUD` 压过两者。其他云端开关同样如此；这个的区别在于量：离开机器的
  是整条对话流，而不是偶尔的一段。
- **密钥绝不放在配置里。** `llm.cloud_key_file`（默认 `~/.config/charoite/llm_key`，
  权限 600）：config.yaml 会进入备份和截图，而密钥就是钱和访问权。它绝不放进请求体，
  绝不打印到日志或错误里，地址只接受 https。
- **断网时的安全网。** 在第一个 token 发出之前，网络错误、5xx 或网关的坏响应（非 JSON、
  用 HTML 代替流）会退回本地模型，并在 err 日志记一行；401/403/400 则大声报错——否则
  你会在本地工作一个月而浑然不知。第一个 token 之后不再回退：云端开头、本地收尾的提示
  会把两个不同的想法拼在一起。非流式调用（会后处理、纪要、档案摘要）同样回退——它们的
  回答是原子的，没有可拼接的东西。安全网落在此人实际拥有的本地引擎上：
  `cloud_fallback_engine`，设置了 `mlx_model` 时默认 mlx-server，否则 Ollama。云端模型
  的名字不会传给它：本地引擎有配置里自己的名字，外来的名字会返回 404。
- **健康探测知道云端。** `llm_health` 不把网关当作本地服务器：没有可重启的东西，探测
  失败也不再阻塞会后处理——调用本身就有重试和安全网。否则在云端安装上（本地 Ollama 只
  承载 bge-m3），重启会杀掉嵌入模型，没有一场会议能进入图谱。诊断、探测和客户端问的是
  同一对键：有地址无许可意味着本地工作，doctor 必须修本地模型，而不是建议检查网关。
- **区分沉默的网关与思考中的网关。** 首个 token 的截止时间放在流解析器内部：从外部无法
  检查，因为 keepalive 行永远不交还控制权，套接字超时又被每个字节重置。完全的沉默半分钟
  就切断，而 keepalive 流可容忍四倍长——发来存活信号的网关通常是在思考一个长提示，切断
  它等于悄悄把模型换成本地的。
- **密钥到不了屏幕。** 401 的响应体会把密钥回显出来，而错误正文会进入提示卡片、逐字稿
  文件和 MCP 回复——所以在正文变成异常的地方就把密钥剥掉。
- **任何引擎下都留在本机的：** 语音识别、说话人分离、检索与去重的嵌入、NLI。聊天网关
  没有这些的云端等价物，而「完全上云」是另一回事——关于音频的那回事。

## 说话人分离：两遍处理

1. **实时**：每个音频块都被嵌入（ERes2Net，512 维）→ 带滞回的声音
   跟踪器（0.45 阈值、灰区、相对切换规则、新声音需两个一致的音频块
   确认）。嵌入向量仅驻留在内存中。通话中，除回声外麦克风上的每个声音都是
   所有者（`owner_voice.owner_voices`）：麦克风只承载一个人，被拆成
   「Собеседник 1」和「Собеседник 7」是轻量跟踪器的伪影，而不是房间里的第二个人。
   面对面会议保持中性标签。
2. **停止后的离线处理**（src/rebuild_transcript.py）：对完整录音按声道
   重新做说话人分离（sherpa-onnx：pyannote 分段加 ERes2Net 嵌入；实时会话
   听到的声音数是系统声道聚类的提示）；麦克风中的扬声器回声按与系统声道
   语音的重叠切除，短于 10 秒的麦克风声音和短于 25 秒的系统声道声音并入
   相邻声音，片段重新转写。所有者是通话中在自己麦克风上「明显」占优的声音
   （至少占房间内人声的 60%，并领先下一个声音 15 个百分点，回声不计），署名
   取自设置中的姓名（`ChannelLabels`）；没有胜出者时标签保持中性——把别人的话
   署上所有者的名字，比不给所有者署名更糟。其余姓名由 LLM 根据所说内容指派，
   经过完整的可信度校验（`speaker_names`）。实时版本保留为草稿。

## 会后流水线（src/graph_updater.py）

**派生物有护照。** 纪要、复盘和要点都派生自转写稿，每一个都在 `.md.live.json`
边车里保存一对键：最后一次机器写入的字节哈希（`<kind>_sha256`）和来源的哈希
（`<kind>_source_sha256`）——发言加上「录音不完整」的说明（`meeting_source.MeetingSource`，
见下文 №316/№317 段落）。语音不含标题和「共同思考」尾部（`transcript.speech_of`）：
重命名主题会改写首行，带标题的哈希让纪要在第一次重命名后就成了「由另一段语音生成」。
新鲜度只在一处决定——`live_sidecar.derivative_state`：没有文件——生成；机器所有且
语音相同——不调用模型；机器所有且语音变了——重建（旧版本进 `.prev/`）；字节非机器
——人工编辑过，不碰；没有护照——同样不碰：这是知识的缺失而非关于人的知识，旧语料
（302 场会议中 232 场没有边车）不会被锁定为「人工」，护照从此刻起签发。纪要在所有
路径上由同一条流水线生成（`finalize_minutes` + `record_minutes_passport`）；复盘在
调用模型前检查所有权，并在「文件未在我们手下改变」的门下写入。复盘文件名遵循由转写稿
文件名推导的唯一规则（`meeting_stamp.derivative_path`），而不是模型在本次运行中给出的
标题：第二条公式曾让实际语料中约 300 场会议里的 69 场各有两份复盘，归档取的是排序
靠后的那份。「何时生成」的策略集中命名在一处（`live_sidecar.POLICY_LIVE` /
`POLICY_RETRO`）：会后的实时路径总是刷新复盘（除人工编辑过的）——其来源是语音加图谱；
回填遍历只生成属于我们且已过期的内容，不做批量回填。读取错误是「不知道」（UNKNOWN），
不是「人工编辑过」：否则一次临时的权限失败会永远停住实时路径。有实时共同思考的会议，
要点由归档从 `> HH:MM 📌 …` 行生成，不为它们付模型费用；模型生成的回填要点只用于没有
实时环路的会议（导入、恢复）。所有派生物的旧版本放在转写稿旁的 `.prev/`，不放进图谱。
按 mtime 判断的标准被测量否决：302 场会议中有 204 场纪要在时间上比转写稿旧——移动
时间的是重命名、共同思考和修订，不是语音。导入尾部只为自己的转写稿运行回填，并按最终
文件名寻址（`find_final_transcript`：此时 graph_updater 已按标题重命名了文件）；全量
遍历为手动操作，每场会议一行：生成了什么、跳过了什么、为什么。

1. LLM 从逐字稿中抽取 JSON：标题（2-3 个词）、参与者、主题、决策、
   行动项、实体、核心（Cores）。
2. 图谱更新：带 `[[Folder/Name|Name]]` 链接的会议笔记，对 People/Systems
   节点做 upsert（事实带日期，历史永不抹除），核心（Cores）——“Status”
   整体重写，“Chronicle” 持续累积。每一行 Chronicle 都带出处：谁说的、
   几点说的、逐字引文——全部取自逐字稿，没有一个字段来自模型的回答。引文：
   先做词级精确匹配；若模型转述了原话，则用模糊搜索找到最接近的逐字稿窗口
   （difflib，0.75 阈值），写入图谱的是逐字稿本身的切片，绝不是模型的措辞；
   低于阈值的一律按捏造丢弃。谁与何时：标记由 `transcript.parse_blocks`
   读取——它是渲染器的逆函数，就住在渲染器旁边：引文位置恰好落在一个块内，
   说话人和时间就从那里取，不按行猜测。没有我们标记的外来逐字稿仍走行内路径
   （「10:15 姓名: 发言」，最多向上五行）。姓名只有属于「本场」会议的参与者才被
   接受——抽取出的人员和「Участники (звучали в разговоре)」表头；图谱节点不算，
   否则离职的同事会永远是合法的说话人。没有这项核对时，「Итог:」「Решения:」
   「Присутствовали:」都成了说话人——未做说话人分离的逐字稿有一半是这样的行。
   谁也没认出——引文不署名：缺失比杜撰更诚实。实时纪要（模型在会议中写的）帮助
   抽取，但完全不参与核对——否则在转述里找到的引文会在图谱中获得「逐字取自逐字稿」
   的标记，对捏造的检查就被捏造本身证实了。
3. 归档（src/meeting_archive.py）：“日期 — 标题” 文件夹、人类可读的
   文件名、由提示日志汇编出的 Q&A、结合历史上下文生成的 Summary
   （核心 + 之前两份摘要；未来绝不泄漏到过去——按会议日期截断）。
4. 可选：云端 Claude 将会议纪要与逐字稿交叉核对，并为图谱补充只有
   从历史视角才能看到的链接。被审阅推翻的内容不会继续存在：撤回的行动项从纪要的
   任务区移入「审阅撤回」并附原因，笔记中错误的决定就地标记 ⛔，Charoite 对该会议
   的外部记忆（`sufler.brain: true` 时）会在去掉这些决定后重新发送（此前事实在审阅
   之前就进入记忆，审阅从未追上它们）。
   重建把说话人标签安在了错误的人身上时（严格的「姓名更正」小节：标签 → 姓名并附依据），
   Charoite 会重新标注逐字稿的发言标题与参会者行以及纪要的参会者行，修改前的版本存入 `.prev/`——
   仅在编辑模式且修改已核对时进行，此时云端也会把该会议从错误人物的节点中移走；
   只读模式下不改任何名字，日志指向复审中的小节供人工处理。

每个阶段都会原子写入 `logs/meeting-status/`：macOS 应用显示真实处理进度，云端审阅阶段（进行中、重试、完成、失败）作为 `review` 字段写入同一状态而不改变就绪状态，
失败时保留指向原始逐字稿的路径，并且只在精确的会议笔记实际生成后通知完成。状态文件按「原始」
逐字稿的时间戳命名，这个键也写在状态本身里：新进程（图谱步骤、按改名后的路径重试）按该会议的
路径今天解析到哪里找到同一场会议的记录并沿用其键；路径已失效的记录让位于有效的。过去键是文件
名主干：改名后的失败把「error」写在旧主干下，重试却在新主干下运行，陈旧的状态让这场会议永远
留在重试队列里，每次都从录音重建（30.08 审计）。重建在覆盖逐字稿之前把当前版本保存到
`transcripts/.prev/<名称>`（一代）：实时草稿 `_live.md` 只写一次，两次重建之间的人工修改过去
会消失。会议笔记、归档文件和状态都经过 `safe_write`（tmp + replace），中断的写入绝不会留下空
文件。从原始名称解析最终逐字稿分两遍：先在两种时间戳下找真正的候选（先秒级，再分钟级——带秒
的录音改名后按分钟命名），然后才是 `_live` 副本的抢救；同一分钟内邻近会议的秒级时间戳既不是
候选也不是副本来源。否则秒级那一遍抢救出的副本会遮住分钟级的最终稿，一场已完成的会议被标成
error（首场实时会议，31.08）。

## 知识图谱（一个 Obsidian 文件夹）

```
<graph_dir>/
  Встречи/YYYY-MM-DD_HHMM_标题.md        ← 情节：会议（原始素材，永不丢失）
  Люди/ Системы/ Команды/ Модели/        ← 实体：人物、系统、团队、模型
  Ядра/                                  ← 核心，跨会议主题：Status + Chronicle
  Досье/                                 ← 主题档案 + _ИНДЕКС.md
  Заметки/                               ← 语音笔记
  Встречи-архив/日期 — 标题/              ← 阅读层（便于在 Finder 中打开）
  Документация/Стенограммы встреч/       ← 会议文档（见「重复的几种类型」）
  _MOC.md                                ← 内容地图
```

无论界面语言是什么，流水线都写这些俄语文件夹名；检索也读取演示图谱的英文文件夹
（`People`、`Systems`、`Cores`……）。这是三层 “情节 → 实体 → 社区”（episodes → entities → communities）方案
（同 Graphiti/Zep），落在纯 markdown 之上：grep、Obsidian、git 和任何
编辑器开箱即用。被取代的事实只是标上日期，而不会被删除。

**选择图谱。** 生活的每个领域都有自己的图谱，彼此并列；抽取结果中的
「проект」字段决定一场会议落到哪里。模型不是盲选：提示里带着已有图谱的清单
（含 `_MOC.md` 的同级文件夹），并明确点出工作图谱这个默认值，答案再与已知
名称比对——忽略大小写和分隔符，「Project Alpha」和「Project_Alpha」是同一个
图谱，而不是两个。只有明显与工作无关的主题才会新建图谱；工作会议出现这种
情况就是选错了，因此日志会记录当时已知的图谱有哪些。

**作为记忆的图谱卫生。** 说话人分离的标签（「Собеседник 3」「Speaker 2」）不是人：
它们在 `Люди/` 中不会得到节点，在会议笔记里保持为文本——否则不同会议里的不同的人会
被粘进同一个有上百条入链的文件（28.08 审计：17 个这样的节点）。节点名按去掉标点、
括号和连字符的键比较（「Иван (Иванов)」与「Иван Иванов」是同一个节点），模型回答中
`[[…]]` 内部的换行在写入时被接上——对 Obsidian 来说这种链接是死的。人名还会忽略词序
比较（「Иван Петров」→ 节点「Петров Иван」），话语中的工具格（「с Сашей」）像呼格一样
指向已知的人，粘在真名上的说话人分离标签（「Саша (Speaker 1)」）会被去掉，合并后
留下的重定向占位符会指向其规范节点，而不是把会议收进自己（记忆审计，07.09）。夜间
`scripts/graph_doctor.py` 不用模型衡量每个图谱的健康——断链（活跃文件夹与流水线从不
重读的 `Встречи-архив` 分开统计）、People 中的标签、孤立节点、重复、按名称键与忽略词序
的近似重复、`_MOC.md` 覆盖率——写入 `logs/graph_doctor.json`；晨报显示汇总并按阈值给出
警告（断链阈值只计活跃链接）。

一个解析器 `src/graph_links.py` 为 doctor、云端审阅和各种清理统一判断 `[[链接]]` 是否
有效：完整路径、笔记名、节点头部 `aliases:` 中的别名（与 Obsidian 相同），或磁盘上的
附件。笔记优先于附件（「Linux 1.8」和「v2.json」是节点），否则只要图谱根目录下该路径
有文件，链接就有效；doctor 不维护扩展名清单，绝对路径、`..`、隐藏文件夹和隐藏文件
（`.env`）永远不是目标。`Досье/X` — `Ядра/X` 对以及 tier3 的重定向占位符按设计同名，
不算重复。所有层都用同一个检测器 `src/charoite_graph/redirects.py` 识别占位符——依据
第一个标题的结构（`# 名称 → [[规范]]`），而不是 tier3 的字面标记：云端用自己的措辞
标记它的合并。把云端审阅的修改从沙箱搬进图谱时，每个链接目标都会对照实时图谱和本次
运行新建的节点核对：指向两边都不存在的节点的链接变成纯文本，日志写明文件和目标，被
移除的目标累积在 `logs/graph_unlinked.log` 中，作为新节点或别名的候选——在此之前，这类
链接以断链形式落进图谱。死链在本次运行的「所有」写入之后按图谱的实际状态移除：文件在，
目标就有效。修改的命运无法预测——写入会在决定之后失败——因此「这个节点能否落地」的
探测已删除，移除这一步本身失败时写入裁决「死链仍在」。代价：失去链接的文件被写两次，
两次写入之间的窗口由 doctor 捕捉。

会议笔记的「## Связи」中只有图谱里存在的节点才成为链接；代词或词的残片保持为文本。
人物和系统带有一行「最后提及」，机械地更新；描述是带日期的事实：实质性的新事实会取代
它，并在「## Хроника」留下痕迹（№194），超过十行的机器行移到节点末尾的「## Архив хроники」。
索引 `Люди/_ЛЮДИ.md`、`Системы/_СИСТЕМЫ.md`、`Команды/_КОМАНДЫ.md` 在每场会议后按被
触及的文件夹重建（最新在上），夜间全量重建，而 `_MOC.md` 保持为项目概览加会议列表。
节点头部的别名（`aliases:`——YAML 列表、块或字符串；流水线与检索共用一个解析器
`src/charoite_graph/frontmatter.py`）在查找规范节点时读取，排在精确名称和目标文件夹中的
键之后，且只在该文件夹内：若人或云端这样写了，「ИС 1494」和「Витрина 1494」就是同一个
节点，而同别名的人物抢不走系统；两个节点有同一别名——不猜；重定向占位符不提供别名，
tier3 合并时把重复节点的名称和别名移入规范节点的头部。核心的状态每场会议都会重写，被
取代的状态连同它自何时起生效的日期进入编年——事实有「从」和「到」；以不同状态重新处理
同一场会议会在它那一行后追加说明，破折号不算状态。

「事实已发送到记忆」标记（`logs/brain_sent/<时间戳>.txt`；只在 `sufler.brain: true` 时
写入——默认关闭，此时这一步不拿锁也不留债）记住已发送事实的键（表头按会议，决定按
文本）：重复时只补发标记里没有的，而不是全部重发。标题以功能词结尾（「…разбор」）的
会议主文件按内容识别；改名只移动该会议自己的派生物，绝不移动同一分钟的邻近会议，而且
标题尾部绝不会与功能后缀重合（「Демо live」→ `…_Демо-live.md`，否则 `stamp_of` 会把主
文件当作 `_live` 副本）；合并留下的占位符不进入提示的节点索引。逐字稿重建
（`src/rebuild_transcript.py`）从启动到退出一直在 `logs/rebuild-<时间戳>.pid` 上持有
`flock`——这是「正在运行」的唯一标志：同一场会议的第二次运行看到锁被占就退出，标记在
退出后仍留在磁盘上（锁由操作系统释放）——下一次运行直接覆写它。刻意不按 pid 判断存活、
不删除标记：pid 会被复用，而在别人刚拿到的锁下按名称删除会删掉正在运行的标记。卷不支持
`flock` 时保护关闭，日志会说明。此前累积的标签节点由 `scripts/migrate_placeholders.py`
清理：默认只出计划，`--apply --backup DIR` 把指向它们的链接变成纯文本、把节点移入带清单
的副本并重建索引；实时会议进行中时拒绝执行。

名称匹配多个节点、或与已有节点只差一个字符的实体不会成为节点：名称在会议笔记中保持为
文本，候选写入图谱根目录的 `_Кандидаты.md` 交给人。把节点搁置一场会议是对的；每场会议都
搁置、直到有人打开那个列表，就等于把这个实体作为记忆丢掉——三天内一个系统被搁置了六次，
无人查看。因此同一对搁置的「名称 → 候选」在「第二」场会议中出现时，在它那一行计数，只有
一个候选的错别字会自动在该节点里得到一条 `aliases:`——会议立即落进该节点，并在其
「## Встречи」和日志里留下「按重复」的痕迹。无人参与的合并只在名称中有相同数字时允许
（「Kwen 32B」→「Qwen 32B」）；不带数字的名称（「Препрод」→「Препрот」、「Реестр Витрен」→
「Реестр Витрин」）只得到计数。撤销错误合并就是从 front matter 中删掉别名、从节点里删掉
会议行——痕迹正为此而留。机器在别名旁边留下自己的痕迹——节点 front matter 中的
`auto_aliases:`——并从那里而不是日志里读取否决：一个在 `auto_aliases:` 中却已不在
`aliases:` 中的名字是被人删掉的，机器永远不再合并这一对（日志行只记下「псевдоним снимал
человек」）。把名字也从 `auto_aliases:` 中删掉，机器就可以再次合并——而且可能就在下一场
会议，因为重复次数已在日志中累积。两个列表字段在合并图谱或把 tier3 重复节点折叠进其规范
节点时随节点一起迁移（`frontmatter.carry_list_fields`），因此否决在迁移后依然有效。
`_Кандидаты.md` 是报告和事件日志：重复按它的行计数（「同一对」= 名称、原因和同一组候选），
但行尾不藏任何状态——作为子串存放在人工编辑文件里的状态在清理时丢失，在零写入时撒谎。
已决定的路径只经更新门写入（`rewrite_file`）：在裁决与写入之间消失或在我们手下变化的
节点，是带原因值的日志事件，而不是带解析器类型的新节点，也不是覆盖。真正的歧义（多个
候选）只得到计数：机器无权合并它。

已经作为另一种类型的节点存在（`Системы/X`）、之后又被称为核心的主题，会得到一个并行的
`Ядра/X`——两者无法自动合并，结构不同；流水线在日志里说明，doctor 早上显示这一对——从此
两个节点在 `## Связи` 下都带有一行互指的「смотри также」，只写一次，重试时幂等，这样
审阅者或实体裁决之后的合并就有了可见的原因，而不是 `canon_link` 里的一个谜。

写入没有发生的原因是一个「值」而不是文本：「在我们手下变了」「文件没了」「够不到文件」
是信号本身携带的三种类型，系统自己的细节放在单独的字段里，而不是粘在字符串末尾。每种
情况要求不同的处理：消失的文件无可修复，也无可指责；够不到的文件保持原样，必须大声报告；
输掉的竞争意味着别人写在了上面。原因文本是给读日志的人看的，在一轮评审里就改了两次——
从另一个模块去匹配它会悄悄失效。为「两个」桥调用构建指责语句的地方只有一个：在每个处理器
里手写时，它在同一个提交中就在对同一座桥的相邻调用之间分道扬镳。其余各处按原样打印原因
文本，不臆造肇事者。

去往图谱的文本以「严格」方式读取，不得带入不可读字符：无法按 UTF-8 解码的沙箱文件带着
自己的裁决行进入隔离区，给节点中原本没有「�」的行加上这个字符的修改也一样——原本就有这种
字符的节点仍然可以编辑。桥的一侧同样：纪要在严格读取后重写，带这个字符的条目或撤回原因
不会进入纪要，带它的名字不会进入发言标题或 People 节点，本身不是 UTF-8 的审阅不会被复制进
图谱（会议照样归档）。在此之前，转移以替换方式读取文件并写回结果，于是一个被截断的字节会
永远留在节点里。

当重复节点被改成重定向占位时，被替换的正文会复制到运行隔离区旁、但不受其轮换影响的目录
（`cloud_quarantine/вытеснено/<运行>/`，保留最近 100 次运行）；只有当规范节点连同占位文本
本身保住了重复节点的事实——至少三分之一的内容行且不少于两行，标题和「Решено」之类的单词行
不计，同一次运行中修改过的规范节点按同样规则衡量，本身已是占位的节点无可丢失——占位才会
落地。13.09 之前旧正文只存活在一次运行的快照里。在邻居之后拿到图谱锁（或放弃等待）的工作
进程，若审阅文件在等待期间已更改、不早于逐字稿、且邻居已以「ok」结束审阅阶段，就不会再启动
第二次付费运行（`--force` 可强制）。

## 档案：检索与图谱之间的一层

当被问到"这个主题现在到底怎么样"时，检索返回十几个零散片段，模型每次都要重新
拼装答案。档案就是已经写好的那个答案：当前状态、时间线、已定事项、未决问题、
相关人员——每一条都链接到来源节点。检索**优先**查询档案索引，只在需要细节时
才进入图谱。

**如何生成。** 一个簇 = 一个核心主题 + 其沿 `[[反向链接]]` 的一跳邻域：相邻核心、
会议、文档。主题边界来自人工已经画好的链接，不需要图聚类算法。夜间由本地模型
为每个簇写出五个小节的综述。

**增量更新。** 每份档案的 front matter 里都带有其构成的指纹——来源清单及其修改
时间。指纹未变意味着主题没有变动，因此不调用模型。在通常的一夜里，几十个主题中只有
少数几个被重建。每周一次全量重建（`--full`）仍然有用：增量更新会逐渐模糊簇的边界。

**索引查询**（`Досье/_index.json`）是词法的，基于词干并支持前缀匹配，因此
`qwen` 能找到 `qwen3-32b`。不需要向量嵌入，也不需要运行 Ollama；语义层叠加在
其上。答案中的档案正文取自检索索引快照，而非磁盘：遍历尚未见到的综述在下一次
遍历前不参与答案。

**派生内容不与原始内容平起平坐。** 检索索引中的每个文档都有一个角色，在读取时
根据路径推出一次：原始（会议、节点、文档）、档案（综述顶层文件夹）或服务
（指针、候选、报告——任何文件夹中带服务前缀的文件）。消费者读取角色，而不是
路径字符串。只有原始文档为枢纽加权投出入链票：综述复述的正是它本要投票的那些
节点，加权落到了它恰好提及的对象上（工作图谱中 16 % 的票）。档案仍是链接目标
和「📁」小节，但不占「图谱中找到」的名额，也不作为从节点出发的跳转目标——即使通过箭头指向综述的重定向占位符也不行：
占位符解析器绝不把派生文档当作替代。快照发布现成的切片（原始文档、按规范化键
索引的档案映射），消费者取自己的切片而不是过滤总列表；向量只为原始文档计算。
服务文件不在索引中，但计入答案的覆盖范围，覆盖范围的措辞由外观层、记忆块标题
和线程状态共用的一个格式化器生成：「未搜索：… 索引外的服务文件：N」。按角色的
投票统计是快照的属性（`memory_bench --stats`）。

**可选的云端复核。** 本地模型转述忠实，但看不出关联：某个决定被后来的决定推翻、
某个期限已过、两个节点互相矛盾。Opus 能看出来。当 `sufler.cloud_edit_graph: true`
时它在夜间自行修改档案；关闭（默认）时它只写报告，由人来应用修改。会议记录、
纪要和「## Правки автора」（作者修改）小节永不触碰；每次修改前先备份。

取自 2025-2026 年的实践：社区综述的思路（GraphRAG）、无需全量重建的增量更新与
双层检索（LightRAG）、以事件而非计划触发失效（Graphiti）。递归抽象树（RAPTOR）
被证明没有必要——层级已由链接表达。

## 为什么选这些模型

基准测试与来源——[MODELS.zh.md](MODELS.md)。要点：主模型保持在 30B 级别
（图谱抽取的下限），轻量模型与它一同常驻内存，`num_ctx` 始终显式指定。

## 记忆模型一页速览

- **文件是事实来源。** 不以图数据库或向量存储作为主载体：只有归用户
  所有的纯 Markdown。每条 Chronicle 事实都带出处（谁、何时、逐字稿
  原文引用）。
- **唯一的 LLM 网关——src/llm.py。** 全部聊天调用都经过它，全部嵌入调用
  经过向量之门 `embed_door`（一次请求至多 64 段文本、72 000 个字符；批次、
  整个调用的时限与响应解析都留在那里，模型层只提供地址、名称与传输），
  模块不自行拼 HTTP 请求。每个请求都带 `truncate: false`：
  装不下输入时 Ollama 会以 400 拒绝，而不是悄悄截断（27.09 实测：不带该字段时
  bge-m3 在 2102 个 token 时返回 200，而 `prompt_eval_count` 显示 2048——尾部
  未进入向量）。不认识该字段、自行截断的服务器，向量之门看不见：它的 200 与
  正常的 200 无从区分。收到 400 时，向量之门以 `truncate: true` 重试同一批；
  重试返回向量后，每个地址与模型只提示一次该批中最长的文本序号与字符数（拒绝
  正文未点明长度时给出中性提示：重试返回了向量，若拒绝确因长度，尾部未进入
  向量）；某次调用中没有任何批次从截断重试中获得向量时，无论该调用如何结束，都会清除该提醒。上限是运行器的物理批大小 2048 个 token，
  见 26.09 实测（「检索的实际工作方式」一节中的「以块为单位，而非整个文件」）；
  `options.num_ctx` 不会移动它：`/api/show` 声称 `bert.context_length = 8192`，
  服务器却在 2048 处截断。模型永远取自配置：14.08 的审计发现，配置早已改变之后，
  仍有四个模块在调用硬编码的模型。网关支持两个引擎，由 `llm.engine` 选择：
  `ollama`（默认）和 `mlx-server`——兼容 OpenAI 的 `mlx_lm.server`，其前缀缓存让长会议上
  实时线程的预填充从约 30 秒降到约 0.3 秒（2026-08-14 实测）。无论哪个引擎，嵌入都留在
  Ollama 上（mlx_lm.server 不提供嵌入）。2026-08-15 的正面对比：新传输保持了锚点，但在
  长会议上重现了 JSON 块失败（那里没有严格 JSON 模式），也没有为实时线程赢得时间——它的
  提示按构造就很小——因此生产默认值仍是 `ollama`；该引擎仍作为配置选项，用于长文档问答
  （详见 MODELS.md）。并非每个服务器构建都支持严格
  JSON：未编译语法库的构建会以「structured output is unavailable」拒绝带
  `format:"json"` 的请求（501，其他构建为 400）。统一的一道门按状态码与
  响应体判定（`strict_json_verdict`）：200 且为不含 `error` 的 JSON 对象是
  「yes」；200 且 `error` 含该短语是「no」，其余带错误的 200、空响应体、
  HTML、非对象都是「unknown」；非 200 时响应体任意位置含短语为「no」，其余——404、
  繁忙的 429/502/503——为「unknown」：排队不等于缺少语法。原因取 `error`
  字段或原始响应体，打印时截断到 500 字符窗口，而判定读取完整文本。判定为
  「no」时，客户端记住（服务器地址、实际发出的模型）这一对十分钟——长时间
  运行的进程期间服务器可能已修复——每个进程只在 stderr 用同一条语句
  （`strict_json_sentence`，不猜测构建）提示一次，并把请求去掉 `format` 重试
  一次，改靠提示词。doctor 用廉价的 `/api/chat` 探测向同一道门发问
  （`llm_health.strict_json`，`format:"json"`，一个 token）——仅在模型存活且
  引擎为 Ollama 时；mlx-server 与云端网关不承诺严格 JSON，繁忙或找不到的
  模型也不探测。这类一次性提示——严格 JSON、无法读取的配置、mlx 上的
  外来模型、写不进去的模型租约——共用一个注册表 `src/once.py`（base 层，
  仅标准库）：键是 `(命名空间, 含义)`，含义包含使重复成为重复的东西——
  状态码、响应体、形式、异常类型、路径——而不是整条成品字符串；`forget`
  重新开启一段情节，`reset` 清空一个命名空间或全部。产品线程也只有一条产生路径：`src/threads.py`（base 层，仅标准库）是唯一构建
  `threading.Thread`/`threading.Timer` 的地方，经由 `threads.spawn` 与
  `threads.timer`，名字与角色都是必需的（角色不在固定列表里或名字为空即为拒绝）。
  注册表把角色与 `detached` 原因作为线程上的元数据保存（弱键），测试借此等待自己
  没有 join 的线程；搜索包自己构建线程——它是独立发行版，没有应用注册表。说话人姓名取第一个对象（`parse_json_block`）。在重建
  路径上经过完整的可信度校验（`speaker_names`）；说话人分离的命令行工具只
  保留在对话中出现过、长度 3–15 个字母的单个词，且不能与说话人标签相同。图谱解析保持
  严格——整个回答必须是一个 JSON 对象，因此周围的文字、被截断的回答或回显
  的模板都是该部分的有名称的失败，而不是会污染图谱的猜测。忙碌与其他错误都不会被误判为缺少语法。
- **唯一嵌入模型——bge-m3**（Ollama）：负责语义搜索与核心修订预过滤。
  刻意不设第二个嵌入模型。
- **精度——本地 NLI**（src/nli.py，ONNX）：要点去重与核心修订判定。
  仅用于可容忍延迟的循环；实时提示与既视感（déjà vu）跑在廉价的词干
  匹配上。
- **云端——仅限自愿开启（opt-in）的会后增强**，通过订阅实现（环境中
  没有 API key）。默认情况下会议数据绝不离开本机；没有云端记忆 SaaS，
  也没有此类计划。
- **MCP 服务器**（src/mcp_server.py）把档案与进行中的会议作为 Claude Code
  的工具暴露出去。它同时支持 `mcp` 包的两个分支：2.0 移动了类
  （`mcp.server.fastmcp.FastMCP` → `mcp.server.MCPServer`），而 pyproject
  两者都允许——安装不应悄悄产出一个在导入时就崩溃的服务器。数据根目录在每次
  调用工具时询问，绝不根据代码所在位置猜测：未设置 `CHAROITE_ROOT` 注册的服务器
  仍能启动，但每个工具都不执行工作，而是返回带注册方法（`_recipe()`）的工具错误
  （`isError`）：拒绝不会被当作正常回答，而 MCP 客户端不会显示崩溃服务器的 stderr。
  该错误是包自身 `ToolError` 的子类：否则 mcp 2.x 会把文本换成 “Error executing tool …”，
  原因和注册方法都会丢失。

## 会议如何挺过崩溃

守护进程是应用的子进程，因此它的死法远不止「停止」按钮所覆盖的那些：应用被
重启、看门狗触发、系统在内存压力下杀掉它。有三重机制阻止会议随之消失。

**每个进程一个时间戳。** 逐字稿文件名与原始音频文件名取自同一个精确到秒的
时间戳，且两者都绝不会覆盖已存在的文件。录音接收端以 `"xb"` 打开，因此冲突
是一个可见的错误，而不是静默截断——崩溃两秒后自动重启即触发，也就是几乎总
在同一分钟之内。

**录音的显式交接。** 正常停止时，守护进程通过 `.part` 文件把 `.pcm` 转成
`.wav`，再以原子重命名发布结果。只要 `.part` 存在，`rebuild_transcript` 就
等待；只有守护进程的锁空闲时，它才自己转换 `.pcm`。文件年龄不能决定任何事：
三小时的会议每个通道 345 MB，其 mtime 早在转换完成之前就冻结在 `stop()`。

**启动时的接续。** 任何旁边仍有逐字稿、且不属于当前会议的 `.pcm`，都会在守护
进程启动时触发重建——在保留策略运行之前，这样清理绝不会删掉某场尚无人处理的
会议的唯一副本。孤儿录音在后台链条中逐个重建，而不是一齐并行启动：一次重建就占住
模型和内存，守护进程的启动也不等待它。

stdout 管道断开（应用退出或重启）会触发与界面相同的停止事件：守护进程正常收尾，
写出图谱与纪要，而不是在心跳继续安抚看门狗的同时悄悄丢掉 STT 线程。

**音频消费线程与录音同寿。** `AudioHub` 只有一个循环——`_tick` 遍历：先把每个
通道的数据块写入文件和 STT 缓冲，再运行通道看门狗；保护落在每一个工作单元上，
看门狗最后且总是运行——一个通道的坏块既不会饿死邻居，也不会取消看门狗。过去
看门狗裸露地站在循环里，它每一次遍历的任何异常都会杀死线程：会议的剩余部分
不再被写入，应用只能在最多 100 秒后看到「音频输入停滞」并重启整场会议。失败不会
无声：stderr 一行加给所有者的状态，每种异常类型最多每 30 秒一次；不会宣告通道
丢失——通道活着，出问题的是 hub。健康快照带有 `pump_alive` 和 `pump_failures`
（经 JSON 门进入 `stt_progress`，也进入 `hb`）；自 №313 起应用会读取它们
（`PipelineHealthMonitor`）：泵死亡即录音停止，属严重；连续失败的遍次为警告——见下文系统
健康一段。应用不会因此重启录音。`AudioHub` 的构造器不做任何 I/O：设备由 `discover_captures` 发现，生产路径是
`AudioHub.for_meeting`；测试调用真实构造器，因此生产代码不再需要防御自己的测试
脚手架（DS 与 GLM 关于 №311 的入口评审）。

**通道丢失会在会议文档中留下痕迹，而不只在状态里。** 在 №234 之前，「对话方通道（或
麦克风）停止写入」这件事只以一条 `on_status` 字符串存在：粘性状态、通知、`capture.log`；
通道恢复不会在任何文件里留下痕迹，一天后读转写稿的人看到「对话方在 14:32 沉默」，与谈话
中的停顿无法区分。14–18.09 的测量：36 次录音中有 12 次出现系统音频丢失，一场会议里
「丢失 → 看门狗重启 → 再丢失」最多 21 个循环。现在 hub 有唯一一处把通道状态转换变成
结构化事件（`ChannelEvent`：丢失 / 恢复 / 静默重启留下的空洞 / 直到结束都未恢复；真实
边界是通道的最后一帧，而不是呼喊的时刻——呼喊落后于看门狗阈值和重启；用机器可读的原因
类别代替子串解析）。痕迹只有一个所有者——守护进程（`channel_trace`）：事件写入边车
（键 `channel_events`，以合并方式——停止时的边车转储不再整文件覆盖）、作为一行进入
转写稿的「共同思考」尾部（不是语音：派生物的哈希不变，重建会搬运尾部，归档不会把它当成
要点）、作为 `system` 类型的线程行进入会议线程，不去重、不被云端修改。没有时长阈值——
报告里看起来短的片段就是真实的空洞；按数量折叠：每个通道六行之后，文档里只留停止时的
汇总（「录音不完整：无系统音频 14:32–14:35、14:50–直到录音结束」）。状态的字符串契约已在 №310 关闭，见下文。

**状态的黏性由写入者设定；应用中的层按所有者划分（№310）。** 守护进程曾按三个和两个俄语
标记的子串对 hub 的状态行分类（`is_sticky_status`、`is_sticky_clear`、`is_recording_failure`）：
措辞改动或第四个标记会悄悄改变黏性，而通道「恢复」的通知经由第二个出口 `_emit` 离开 hub，
那里根本不会有标记。现在 hub 的状态是 `stt_runtime.Status`——`str` 的子类，带 `sticky`
（True 设置层，False 清除，None 为普通状态）、`error` 和 `topic`；字段在产生该行的地方设定
（`_announce_losses`、`_announce_back`、四处磁盘故障），通向 `on_status` 的只有一扇门 `_say`，
JSON 由契约模块的一个函数 `status_event` 构建：`error` 总是有，`sticky` 和 `topic` 仅在设定时
出现。`src/` 中不再有子串分类器。应用里不再是三个写入者共用一个 `String?`，而是按主题划分的
`stickyLayers`：`channel_loss`（守护进程）、`capture`（麦克风未进入 ScreenCaptureKit 流）、
`notifications`（通知权限被拒）；每个写入者只清除自己的层，守护进程的清除不再抹掉「没有麦克风
权限」，屏幕上的一行按优先级用「 · 」连接所有活跃的层，开始录制清除全部。线上的布尔 `sticky`
与 `topic` 并存：0.82 版应用只读布尔值，没有主题的新守护进程落入通道丢失层。

**「录音不完整」的说明是关于录音的事实，不是发言；派生物只有一个来源。** 在 №316/№317
之前，派生物（纪要、复盘、要点）只有一个输入——一段文本，每个消费者自行决定往里掺什么：
`_fit` 折叠，守护进程的草稿裁窗口，`debrief_excerpt` 取文件的头尾，`speech_of` 切掉
尾部。「对话方缺席 40 分钟」这一事实要么作为发言到达模型（MCP 纪要读整个文件连同尾部），
要么根本到不了（其余所有路径）——18.09 的纪要看起来是完整的。分段小结只由守护进程在停止时
写入：守护进程死亡就没有这一行，尽管事件全在边车里。现在派生物的来源是一个对象
`meeting_source.MeetingSource(speech, recording_note)`：发言（`transcript.speech_of`）
被折叠和窗口裁剪，`fact_check` 也据此核对引文；说明（`channel_trace.recording_note`——与
守护进程停止时写的同一行，`summary_of`）作为独立块进入提示，位于转写标签之外、所有裁剪
之后（`LLM.recording_block`，ru/en/zh，附规则「不要当作发言引用；丢失通道的沉默不能理解
为同意」），以机械方式写入文档（`meeting_source.with_note`——让模型「在风险里提一下」无法
验证），护照哈希的是发言加说明（`sha()`）：没有说明时生成的纪要在说明出现时恰好过期一次，
护照的写入者和新鲜度的读取者是同一个函数。每个提示构建者（守护进程的草稿和「纪要」、MCP
纪要、重建、`graph_updater` 的复盘、回填遍历）都把这个块放在自己的裁剪之后；复盘从发言的
末尾取窗口，并把实时尾部要点作为独立的「模型的笔记，不是发言」块接收。重建通过尾部格式的
所有者（`transcript.append_note`；没有该节则创建）把小结从边车恢复到「共同思考」尾部，第二次
运行不会重复。

**手机录音为何停止——是随文件一起走的值。** 07.09 一场会议以三段到达 Mac，中间没有任何来电，
而磁盘上没有原因：伴侣应用的 `stop()` 释放会话并交出文件，`lastStopReason` 是给屏幕看的本地化
字符串，随进程一起消亡，Mac 看到的是三场普通会议。在 №200 之前，各条停止路径无需命名原因：
编解码器连续错误、通话后预算、停滞看门狗、媒体服务重置各写各的字符串。现在唯一让 `isRecording`
变为 false 的函数接受必填的 `stop(reason:)`——编译器就是闸门，新的停止路径不说明原因就无法关闭
文件——录音器在音频旁写入清单 `<文件>.json`（`Recorder.StopRecord`：kind stop|rotate、来自封闭
enum 的 reason（每个值只与设置它的代码点一起存在——`disk_full` 不在列表中，因为没有任何检测）、
`at`、秒数、序列词干（同一场会议的分段彼此相认）、由终结代理为「自己的」文件而非当前录音器
设置的 `finalized_ok`）。队列的单位是「对」：`Inbox` 一起搬运、救援、发布（清单先以 `.part`
发布，音频最后，两者使用同一个去重后的名字——iCloud 中的同名冲突不会把清单粘到上周的会议上）、
归入 Sent 并一起删除。`current/` 中没有清单的孤儿得到 `no_stop` 和最后一帧的 mtime——事实是
「没人关闭这个文件」，而不是猜测「进程被杀」；`stop()` 在进程死亡前来得及写下的清单会被保留。
在 Mac 上，`import_meeting` 在 `graph_updater` 之前、在「没有语音」分支之前，把清单转换为拥有
频道丢失的同一条痕迹的事件（`channel_trace.phone_event`，kind `stopped`，原因放在 `reason`——
`cause` 属于 hub 的字典），因此派生物的护照从第一次生成起就把发言与说明一起散列；措辞和痕迹行
分类器只存在于 `channel_trace`，文档中写入的是所有尾部读取者都已认识的同一条小结行
（`note_in_tail`、重建、`meeting_source`），而不是第二种行。手动停止不产生事件。两种非自愿停止
都进入「录音不完整」小结——终止性的（「已中断 19:02（未记录停止）」）和轮换（「被打断 19:02
（通话后麦克风未恢复）— 若录音已恢复，则在下一文件中继续」）：手机在关闭文件的那一刻承诺继续，
却无法知道通话后的启动是否真的发生，因此措辞陈述观察到的事实而非未来（输出轮 DS）。文档的尾部行是边车的派生物，只有一个写入者，且受 compare-and-set 闸门保护
（`channel_trace.tail_with_summary` 基于 `safe_write.rewrite_file`），导入、核对与重建共用——
核对遍历的文件可能正被另一进程中的重建重写（第 2 轮，DS 与 GLM）。事实由核对
消费，而不是导入时的一次性读取（输出轮 GLM）：`reconcile_manifests` 在每次扫描时运行——在音频
已移入 `done/` 之后才到达的清单，通过导入边车的 `source` 字段与音频重新配对；位于 `done/` 中而其
转录缺少事件的清单会补写事件（幂等）；导入文件夹中的孤儿清单在清理前等待一小时——iCloud 送到
一 KB 的 JSON 远早于一小时的音频。在保留期中清单随音频一起消亡。

导入的逐字稿来自哪个文件，记录在它自己的边车键 `transcript_origin` 中（`{name, size, kind}`，kind 为 `audio`/`subs`/`text`）：由三个导入分支的共同尾部写入一次，所有者是 `src/transcript_origin.py`；重复检测先读该键，只有缺少该键时才回退到 H1 尾部「— импорт X (N Б)」，两者使用同一条（名称，大小）匹配规则（№262）。

**归档摘要是带护照的派生物；其来源是喂给模型的内容，而非发言。** `Саммари.md`——一分钟读完的摘要，
人们最先打开的文件——只生成一次（`_gen_summary` 跳过任何非空文件），此后不再更新，而云端修订却在不断
重写它所依据的纪要（№238/№239）：19.09 当天，298 个归档文件夹中有 74 个的摘要比其纪要更旧。输入轮（DS 与
GLM）收敛于一个机制，并抓住计划中的三个漏洞：摘要的来源不能像其他派生物那样是「发言 + 说明」——会议结束后
发言不再变化，护照将永远 FRESH；在 `meeting_archive` 中建立第二条写入接缝会与 `retro_fill._write_derivative`
的闸门分叉；`rename_meeting` 用裸 `replace` 重写摘要字节（文件夹名存在于其 H1 和链接中），带护照后每次
重命名会议都会永远冻结在 HUMAN。现在 `summary` 类型的来源是输入的规范形式（`summary_source_sha`：纪要、
要点、复盘和转录尾部的截取、抽取的决定、录音说明——绝不包含提示模板的措辞或配置语言：配置只决定「新」文档
用什么语言，无权重写旧文档）。纪要与从中抽取的决定在裁剪之前先做规范化（`task_line.without_statuses`，№392）：
所有者的 `[x]`/`[-]` 标记、任务控制备注与插件字段（含截止日期）都是会后的事务记录，而非会议内容——因此
勾选任务既不会使摘要陈旧，也不会传给模型，而无状态机器文本的散列保持不变：遗留护照无需重建即为
FRESH。从纪要中抽取的决定完全不带复选框：否则所有者的 `[x]` 会经由“没有做出决定”的兜底路径，以未完成的
`- [ ]` 出现在 `Саммари.md` 中。`live_sidecar` 拥有护照契约的两半——`derivative_state` 判定，`write_derivative`
（从 `retro_fill` 迁入，所有类型共用一条接缝：快照 → `.prev/` → expect 闸门 → attest，且不给不存在的转录
发护照）写入，`retouch` 在机械重写后重置字节散列而保留来源。实时路径与回填遍历共用一个策略——MISSING/STALE：新会议是 MISSING，复审交付通过纪要使摘要陈旧（STALE），
任何自动路径都不触碰 UNKNOWN——对 298 个遗留文件的"不知道"不是在首次触碰时用模型重写它们的理由。
摘要不做 FRESH 重建——所有影响输出的内容都已在散列中。空文件对所有种类都是 MISSING——由唯一的判定函数
而非每个写入者决定。结果作为值（`SummaryOutcome`：已认领 / 已构建 / 未触碰 / 已跳过 / 失败 / 已拒绝）沿整条接缝链
（`write_derivative` → `summary_pass` → `archive_meeting` → 调用方）通过返回值传递，绝不在上一层重新读盘
推断——回填报告曾对机器刚刚重写的文件打印"跳过：fresh"。遍历模式同样以枚举传递（`SummaryMode`：auto /
adopt / rebuild），在策略旁只有一个翻译器将其映射为策略——而不是"策略 + 标志"对：空策略在 Python 中为假，
接缝上按真值代入默认值会把"什么都不构建"悄悄变成默认值。没有护照的遗留摘要只由显式命令处理：
`retro_fill --summary=adopt` 为完好的遗留摘要无需模型颁发护照（附 `summary_adopted` 标记）——材料不比
文件更新、文档结构是我们的、录音说明为空或已在文本中——且不构建任何东西；`--summary=rebuild` 先认领，
再重建其余部分（19.09：298 个中 224 个完好、74 个陈旧）；遍历结束时打印结果统计。认领在 `archive_meeting` 内部、材料副本刷新之后
进行，与构建使用同一文件夹和同一规范快照。录音说明以事实块的形式在材料之后进入摘要，并作为一行写入文档
（№317），而不是纪要截取内的一行零散文本。清单不携带护照状态的副本——读者调用 `summary_state()`。

**会议的任务正本同样是带护照的派生物。** 每个会议只有一份任务正本——归档文件夹中的 `Минутки.md`，「任务」标签页显示其中各行。
在 №366 之前，每次归档都会用机器来源（`transcripts/<stem>_minutes.md`）的字节覆盖它，抹掉用户打的勾（№370）。
现在 `meeting_archive.lay_canon` 以 `canon_minutes` 护照写入正本，与摘要、要点同一机制：只有当正本字节仍是归档器自己写入的（MISSING / STALE）时才会重写。
任何他人修改——来自应用或笔记插件的勾选、夜间检查、改动或删除的行——都会使其成为 HUMAN，这样的正本不再被触碰，日志中记一行 `kept` 以及与机器版本不同的行数（把机器修改合并进已编辑正本是 №391）。
来源与正本以文本模式读取，与判定函数完全一致——严格 UTF-8 与通用换行，从不使用 `bytes.decode`，因此 CRLF 来源得到判定函数能复现的护照；来源只读一次，正本得到这段文本及来源的时间戳（`safe_write.write_text(times=…)`）。
文本已与来源相同的正本永不重写；没有护照时按比较过的文本认领，并带 `canon_minutes_adopted` 标记。没有转写稿时任何分支都不写护照（侧车会成为孤儿）。非 UTF-8 的正本原样保留（`kept`），只能由人重新保存。
结果是一个值（`CanonOutcome`：created / updated / unchanged / adopted / kept / refused / failed），位于 `Archived.canon`；管线与修订投递打印 kept、refused、failed，回溯遍历与 `meeting_archive --all` 打印汇总。
摘要材料仍然严格读取：无法读取的材料使摘要处理以 `failed`（「материал не читается: Минутки.md」）结束，不重建、不写护照，归档继续进行。
`Документация/Стенограммы встреч` 中的副本就是正本的字节，由 `copy_to_vault_docs` 在归档之后写入（过去管线在归档之前复制）：应用搜索按内容哈希去重，副本必须与正本一致。重命名会议时经 `retouch` 重写正本并保留护照；人工修改过的正本同样替换文件夹名，但不重置护照，正本仍视为人工修改——与摘要同一规则。

**系统健康只有一个汇总和两个界面，而不是四个各自的裁决。** 在 №139 之前，每个健康信号都有自己的界面
和生命周期：录音问题只在会议期间存在于 `SuflerService`；最近一次处理的错误是菜单内的一行；夜间处理
只显示在「今天」屏幕上，且其服务在该屏幕出现时才懒加载——19.09 的 `logs/nightly.json` 显示 `slept`、
跳过四个步骤，却无人读取；Ollama 在菜单视图内被第二个探针再次探测，结果存于视图 `@State`，未本地化，
并且被「会议已就绪」遮挡一天；守护进程的 `pump_alive`/`pump_failures` 自 №311 起随每次心跳到达，却在
解码器边界处消亡。输入轮（DS 与 GLM）收敛于一个机制并否决两个：扩展会议范围的粘性层（每次启动都会清空，
会议之外没有生命周期）以及带 `HealthReportable` 协议的新服务（五个写入者一个读取者的繁文缛节）。现在
`HealthRollup.rollup(recording:isRecording:processingError:ollama:nightly:)` 是紧邻
`PipelineHealthPresentation` 的纯函数——该层本已拥有「一种呈现——多个界面」的规则；菜单栏图标与菜单状态行
读取同一个裁决。事实的所有者留在原地：`PipelineHealthMonitor`（现在也解码泵计量：泵死亡即录音停止——
严重；连续失败的遍次——警告，№313）、`MeetingProcessingService`、`OllamaRuntimeService`（首次探测前的真实 `.unknown` 状态——旧默认值 `.running` 让图标断言一个无人
核实的事实）、`NightlyStatusService`（标题为纯函数；没有 launchd 代理时 `.never` 表示「未配置」，对图标
而言不是问题；有代理时 `.never` 表示夜间处理从未运行）。新鲜度归所有者，通过唯一的调度器 `HealthClock`
（启动后首次读取，不在图标的渲染路径上，之后所有者共用一个间隔；打开菜单只是触发同一次刷新）——同一图标上
两个信号节奏不同、由视图决定何时探测，正是输出轮的严重问题。谁给哪个界面着色是一条策略 `HealthPresentation`：
图标取最差等级，「录音中」旁的圆点只取录音等级，菜单行顺序为工作 → 问题 → 「会议已就绪」 → 空闲，处理错误
使用所有者的标题（`errorHeadline`），而非第三份词典。等级由表格测试钉死：**红色只留给实时录音中的数据丢失**（磁盘故障、
泵死亡）；处理错误、沉默的 Ollama、错过的夜间处理为黄色——源文件保留，丢失的是一小时流水线或一个夜晚，
录音无损。「录音中」旁的圆点是录音的健康，而非 REC 指示灯：过去健康的录音是红色，而降级的录音是黄色，
「放下一切去看录音」的反射在错误的颜色上被训练。没有新的守护进程、看门狗、Ollama 定时器或通知流：
№68 的裁决依然有效——汇总只折叠已有的信号。启动前的磁盘空间预检是新信号，另立卡片（№319）。

## 层边界（docs/design/layout.json）

`src/` 是一个导入根：平铺模块与图谱包 `src/charoite_graph/`（№424）并存，其中的层（base → runtime → llm / cloud / audio → meeting → app，graph 只依赖 base，使图谱搜索可以脱离应用环境安装——№365）按导入事实存在，
但在 №320 之前除了作者的记忆和一次性测量，没有任何东西约束它们。移动文件时断裂的不是一处而是三处：导入、
谁通过路径启动谁（应用的四个文件提到 `src/daemon.py`，其中包括启动本身和「代码是否内嵌」的检查；`code_root()` 从自身位置推导代码根）、以及文件所在位置。
因此唯一的真相来源是机器可读的布局 `docs/design/layout.json`：模块 → 层的表、箭头方向、仍指向上层的边的
白名单（每条附有撤销它的卡片；由 `scripts/layout_map.py --regen` 生成，绝不手工计数——当前数量见 `docs/design/layout.md`），
以及带理由的手动入口点。两个集合分开：入口点是可执行文件（`scripts/*`、`app/*.sh`、经 AST 确认带真实 `__main__` 守卫的 `src/*.py`），每个要么被代码提及——Swift、shell、CI workflow、pre-commit 钩子、python 子进程——要么声明为手动；被提及的路径是代码和散文（文档、配置）按路径提到的一切，每一个都必须存在——给人的提示和 README 中的步骤在移动后不能撒谎，但被提示提到的库不是入口点。提及从代码而非散文中读取：python 字符串字面量经 AST 且不含文档字符串，Swift 和 shell 不含注释。所有测量来自同一份清单：一次遍历 git 管理的文件、一张文件分类表（代码、散文、测试、带日期的评审、范围外）、每个文件读取一次并解析一次——解析失败的文件成为一条问题记录，绝不是回溯也绝不是静默跳过；按位置成为入口点候选的文件在构造上即为代码（python 只有带真实 `__main__` 守卫才成为入口点，shell 脚本本身即是），与候选不一致的表规则是一条红线而非静默优先级；测试在测量范围之外（它们构建合成目录树），带日期的快照（评审、发布说明、文章）描述当日的代码，不做检查。`--regen` 绝不写入加载器会拒绝的工件。工件的字段只在代码中声明一次（`scripts/layout_map.py` 中的 `_SCHEMA`），每个字段有类型和一个说明由谁写入的类别：`measured`——测量，每次 `--regen` 都会重写（边的端点对、时间戳、哪些可执行文件有契约）；`seed`——机器最多在记录诞生时、且代码能证明时写入一次（按代码推断的运行契约），此后该字段属于人的决定；机器无法播种的记录（`none` 契约）由人完整写入；`decision`——只由人写入。对顶层键而言，类别是由测试守住的约定：`--regen` 重建 `measured`，从不触碰 `decision`。声明是封闭的：未声明的字段是加载错误，因此同一事实的第二个载体不会在没有经审阅的代码改动的情况下出现在 JSON 中——自由文本的 `notes` 块正是这样过时的，现已删除。债务只打印、不存储：地图按撤销它们的卡片（`ticket`，开头为 `№…`）对逆向边、没有探针的入口点和文件夹名字面量分组，`--regen` 只打印变化；没有任何门禁读取这个数字。存储模式是值而非散落的字面量：`charoite_graph.graph_schema.GraphSchema` 声明文件夹名、章节头和原始文件标记，其不变量（`__post_init__`）会拒绝正则式的名字、位于排除项内的档案目录以及同时属于另一角色的角色，而 `src/charoite_schema.py` 以字面量保存唯一的 `CHAROITE = GraphSchema(…)` 值。包只询问模式，从不使用字面量：角色是该值的谓词（`is_node_path`、`is_dossier`、`is_service_name`、`excluded`、`is_raw`、`is_meeting_link`、`is_history_head` 等），全部以同一种形式 `text_norm.fold`（NFC、大小写、ё→е、全角拉丁字母和数字）比较——也就是搜索早已用于词和路径的形式。`GraphSearch(schema=…)` 默认为 `PLAIN`，即没有角色的存储（没有节点、没有档案、没有排除项），应用入口 `graphs.open_search` 传入 `CHAROITE`；`NodeIndex` 与 `dossier.scan` / `clusters` 以必需的关键字参数接收模式——只有 Charoite 调用它们，忘记传模式是 `TypeError`，而不是会议中空的节点索引。`Doc.role` 与 `Node.person` 由仅在构造时传入的模式推导（`init=False` 字段），测试夹具无法绕过谓词塞入角色。向量缓存按 mtime 和块数核对：块数上限取决于文件是否为节点，而这现在由模式决定。名称列表的形式由唯一的入口 `graph_schema.as_names` 为模式的元组字段解释：字符串是一个名称，元组和列表原样保留，其他一律拒绝；`dossier_dir` 和 `meeting_dir` 为 `str | None`（`None` 表示存储没有该角色）；注解不是 `str`、`str | None`、`tuple[str, ...]` 之一的模式字段是类错误。`scripts/layout_map.py` 中单独的守卫从类注解读取字段表、从该调用读取值，在图谱包（`package_entries` 各入口的闭包，即包探针复制的同一集合）的字符串字面量中寻找这些名字的副本，并把每个副本作为带卡片的 `folder_literals` 债务保存；`folder_literal_exemptions` 以书面理由宽恕一个副本，两者都像这里的一切记录一样双向核对。自 №422 的 PR B 起债务为零，包自身不再保存名称常量。`tests/test_graph_schema_roles.py` 对模式做轮换——`CHAROITE` 的每个名称变成一个 ASCII 记号，相同名称对应同一记号——用轮换后的名称构建同一张图，并要求在反向替换后搜索、档案和节点索引的可观察行为相同：残留的字面量不可能等于记号，因此会表现为不一致。轮换发现了档案索引只是借助 Charoite 的 `_` 前缀才成为服务文件；现在它按自身名称成为服务文件。门禁是 `tests/test_import_boundaries.py`，

（`package_files` 对形状投影 `artifact_name`）双向比对——多余或缺失的模块会成为带名称的一行，而损坏只在归档副本上验证；
构建需要 `ci.yml` 的 `env` 中所固定版本的 `setuptools`，缺失或版本不同时会以确切的安装命令失败，而不是跳过探针。
wheel 还要与其声明对照（№446）：`packages/charoite-graph/pyproject.toml` 只有一个读取者，METADATA 由 `importlib.metadata` 直接从归档读取，门禁的各行是一张带依赖关系的类型表——Name、Version、Requires-Python、License-Expression 与 Requires-Dist 按原样与声明相等，METADATA 正文等于包的 README，wheel 中的许可证文本等于文件，包的每个第三方导入都已声明（且声明的都被使用），包的每个依赖在根清单中写法相同。每种类型都有自己的损坏副本用例，README 示例取自制品的描述，并在解压后的 wheel 上运行。

环境也有自己的层。那就是 runtime，路径规范就住在那里：base 或 graph 层的模块不导入它，
也不以任何形式触碰环境（环境变量、主目录、自身文件的位置、导入时的 `sys.path`、动态导入）
——路径作为参数传入，由能看到 runtime 的层中的调用方组装（№365）。正是这一点让图谱搜索
可以脱离应用安装。

每个可执行文件在同一份工件中还带有运行契约（`run_contracts`），
`tests/test_entry_points_contract.py` 通过运行进程而非阅读来验收它：`help`——在隔离的
数据根下 `--help` 以 0 退出；`refuse`——未指定根目录的启动以退出码 5 拒绝并打印方法（见
「代码与数据各自的位置」）；`none`——没有安全的探针，入口点不运行，原因作为公开的债务写在
地图里。起因是同一类问题连续五个 Critical：关于进程行为的断言，从未经任何一次进程启动验证。
`scripts/preflight.sh` 是评审前的本地汇总（机器负载、静态检查、完整 pytest、改动应用时的
swift、针对区间的变异测试），并有意不重复契约检查：它住在 pytest 里，CI 和变异器都会运行。

## 如何停止录音

停止不是一个动作而是一段等待：守护进程要写完音频、跑完会后流水线并释放锁，而在旧进程
真正退出之前，应用不能开启新会议。这段等待过去散落在五个标志里——于是一个挺过 `SIGKILL`
的守护进程能让应用永远停在「正在停止」，「停止」按钮毫无反应。

状态转换现在集中在一个纯类型 `ShutdownMachine` 中——阶段（`idle`、`waitingDaemon`、
`stuck`、`done`）、事件（按下停止、守护进程退出、轮询节拍、强杀超时）和动作（关闭采集、
再次轮询、报告、强杀、结束）。它不引用服务，因此每条弧线都能在没有运行进程的情况下测试。

时间：8 秒时 `terminate()`，12 秒时 `SIGKILL`，13 秒时备用定时器，之后每秒轮询两次。
等待 30 次后阶段变为 `stuck`——应用用平实的话说明情况，并继续每 5 秒轮询一次，再次按下
「停止」是强杀的请求而不是空操作。

有一条规则把设计维系在一起：事件进入状态机，动作通过服务中的唯一入口出来。评审中同一个
缺陷出现过两次——状态机里声明了一个事件，有绿色的测试覆盖，而服务从未真正发送过它。这样的
测试钉住的是系统并不具有的行为，比没有测试更糟。

## 重复的几种类型

图谱会积累性质不同的重复，每一种由自己的机制处理——把它们混为一谈，就会修错
地方。

**核心节点的概念性重复** — 同一个话题被抽取器在不同会议里拆成了双胞胎（「API
访问配置」与「获取令牌」）。词面重叠为零，因此只有语义能找到它们：bge-m3 挑出
候选，NLI 判定每一对，`tier3` 在 `sufler.tier3_auto_apply` 下合并编年。该流程
每夜运行，并在每场会议后增量执行。

**归档文件夹绝不链接本图谱中没有的笔记。** 文件夹里的 `Граф.md` 把 Obsidian 指向会议
笔记，但文件夹与笔记分道扬镳是常态：会议属于哪个领域是在运行开始后才依据逐字稿决定的，
于是一场私人会议作为笔记进入它自己的图谱，而更早的那一遍已把文件夹留在了工作图谱里。
没能落地的笔记也会这样分开。这样链接就永远是死的：死链移除在写这个文件夹之前进行，看不到
它。因此只有笔记存在时才写链接和 Finder 快捷方式；否则文件里留一句话告诉读者去哪里找，
并删除之前运行留下的快捷方式。16.09 在工作图谱上实测：278 个文件夹中有 20 个指向虚空，
其中六个是最近的。

**逐字节相同的文件副本** — 流水线有意把会议文档写两份：原件写入
`Документация/Стенограммы встреч`，副本写入 `Встречи-архив/<日期 — 主题>`，
以便从 Finder 直接打开该文件夹。在工作图谱上这是 173 组、6.4 MB——翻倍的
iCloud 同步与翻倍的手机占用。`scripts/dedup_graph.py` 在 `sufler.dedup_files`
下把副本换成硬链接：两个路径都照常可用，字节只存一份。检索不必等待夜间任务
——它在遍历时就对内容做哈希并只保留第一份副本，因此模型绝不会在同一上下文里
收到两遍相同的文本。

**iCloud 冲突副本**——`Минутки.md` 旁边的 `Минутки 2.md … Минутки 12.md`。我们的
代码从不生成这种名字；它们恰好出现在归档器每次都*原地*改写会议文档（`copy2`
覆盖已有路径）、无论内容是否变化的地方——9 月 23 日共 7 594 个，任务页因此把同
一条待办显示多达十次。会议文档的写入方现在统一经由 `safe_write.copy_if_changed`
与 `write_text_if_changed`：字节相同就不写，有变化则经临时文件再 `replace`，材料
副本保留源文件的时间（归档新鲜度按 mtime 判断）。归档文件夹只有一个写入方：云端
审阅把自己的文件交给 `archive_meeting(extra=…)`，不再自行覆盖。
`scripts/dedup_graph.py` 的第二条规则把与相邻原件逐字节相同的副本移出图谱，放到
`backups/<图谱>-<哈希>/dedup_copies/<批次>/` 并写清单（`--apply-copies` 或
`sufler.dedup_copies`，默认关闭，与 `dedup_files` 互不影响）；内容不同的副本只
报告。`graph_doctor` 会计数，回归会出现在晨报里。

## 检索的实际工作方式

两路独立信号经 RRF 融合：词法（词干、IDF、查询覆盖率、时效）与语义（通过本地
Ollama 的 bge-m3）。单靠任何一路都不够——词法能命中向量无法区分的内部标识符，
语义则弥补提问用词与笔记记录用词不同造成的词汇鸿沟。

**会议期间守护进程的记忆是同一设计的 Python 版**（`src/charoite_graph/graph_search.py`）。
在 №250 之前，实时循环通过 HTTP 询问一个单独的记忆服务器，而在工作图谱上它要 2.6–22 秒才
回答——即时回答的预算是 2.5 秒，所以实际上它在没有记忆的情况下运行。现在索引住在守护进程
内：项目图谱的文件，不含会议归档和逐字稿副本（3 160 个文件不到两秒就预热完毕），基于词干
的 BM25-lite，带 IDF、长度归一化和有上限的枢纽加权——一个 280 KB 的所有者节点不再对每个
查询都浮上来——时效、档案综述优先、从找到的节点沿 `[[链接]]` 跳一步，以及同样的诚实门。
向量按块计算（标题、面包屑），按 mtime 缓存在 `data/graph_search/`；会议期间只嵌入查询，
文件在会后（上限 45 秒）和夜间索引。一次热查询约 0.1 秒词法工作，外加 Ollama 空闲时的一次
嵌入调用。

**答案绝不声称未读部分已被核查。** 索引有意不含会议归档和逐字稿副本——否则冷遍历无法在
几秒内完成。在工作图谱上这是 14 789 个文件中的 11 506 个，其中 1 945 个归档文件含有决定行。
答案模板过去说的恰恰相反（「归档里大概没有」），断言核查了从未打开的内容。现在每个否定回答
都带上被排除在外的部分：字段来自遍历本身而非配置的清单，因此没有归档文件夹的图谱不产生
附注，文件夹名不同的图谱也不会被说成未读。遍历到了却打不开的文件同样计数。措辞放在外观层
的一张表里，附注说的是「单独的片段」——主题综述是遍历包括归档在内的整个图谱生成的，声称
相反就是反向的撒谎。

**指向已合并节点的链接指向规范节点。** 关于同一事物的两篇笔记合并后，重复的那篇留作两行
的重定向文件。检索过去把它当作普通文档：入链喂给了占位符而不是规范节点，从节点出发的一跳
在那里走进死胡同，答案里它占着一个名额、内容只是一个箭头。在工作图谱上（3 199 个文件、
404 个占位符）这是 1 048 条指向死文件的链接和 40 次没发生的跳转。合并链带环路保护和深度
上限展开。答案中的占位符在排序前被替换为其规范节点，名额不会丢失。

**邻接按路径而不是文件名作键。** 点名了文件夹的链接必须无歧义地解析——作者已经给出了这种
确定性，而以名称作键把它扔掉了。17.09 在工作图谱上实测：41 409 条链接中有 3 532 条落到了
被点名文件之外的文件上，系统性地落到摘要而不是核心上，因为摘要每夜重建、总是更新。修复后
没有一条链接落错；17 条链接指向已不存在的路径。

解析住在 `LinkCatalog` 中，每一代索引一个链接目录。对外有两个层级：`named` 回答「被点名」
的是哪个文档（目录中有这个路径——就用它；点名的路径背后没有文件——是未命中，而不是去找
同名者；裸目标走名称目录，那里活文件总是胜过占位符），`live` 回答背后站着哪个「活」文档——
占位符经规范映射展开，占位符后面还是占位符则诚实地回答「无处可去」。展开放在这里而不是每个
消费者（入链投票、跳转、答案中的占位符替换）那里，因为它们各做各的，在裸目标上都会失手。

目录每个快照构建一次，与文档和投票在一次赋值中一起发布：当文档与目录分开进入外界时，一次
检索可能看到新文件配旧解析，并在其快照已不存在的目标上崩溃。赋值本身是一个带强制基准的
操作：遍历第一行就在锁下取得代次并显式交给发布者——发布者无法重读该字段。「基于一个快照
做决定、写入另一个快照」因此变得无法表达，而不只是在文字中被禁止；连续三轮评审在遍历的
不同分支里抓到的正是这个问题，现在有一个测试守护这个形态（恰好两次赋值）。

谁拥有一个键——名称或路径——在各处都由同一个函数（`owner_key`）决定：最新的优先，日期
相同时取字典序较小的路径，因为节点的日期就是它的 mtime，而检出、图谱复制或云同步都会移动
它。在此之上唯一的优先级：在名称目录中，活文件胜过占位符。

修复对排序的影响（30 个查询，前 5）：查询的词法覆盖率完全没变——前后都是 0.989，所有重排
都发生在「完全」覆盖的文件之间。变化的是同等相关度下展示谁：摘要占的名额减半（34 → 17），
原始节点增多（47 → 61），中位年龄 10 → 9 天。枢纽加权无需重新校准：处于上限的节点 462 个
对 467 个，是同一批。

**裁决是一个字段，而不是前缀。** `brain.vault_search` 返回一个 `Result`：`status` 取
*confident* / *weak* / *unverified* / *empty* 之一，`fragments` 是进入提示的内容（档案与
片段，不带表头、不带标记），`text` 是给人看的呈现。没有嵌入时（会议中 Ollama 忙）词法匹配
为 *unverified*，绝不是 confident，也绝不是「归档里没有」；「weak」——诚实的「归档里几乎
什么都没有」——只有在向量缓存覆盖至少 80% 的索引时才会给出。档案在裁决中算作证据（其关键词
对查询的覆盖），因此没有片段的综述绝不会是「empty」。该「说」什么由外观层的一张表决定
（`LEAD` / `ABSENCE`，覆盖所有状态；「未核实」背后的原因——嵌入模型忙或缓存不完整——是结果
的一个字段），并由一个构建器 `memory_block` 按比例在图谱节点与归档片段之间分配提示预算，
而不是让节点吃掉归档；裁决为 confident 时片段优先，节点只得到剩余部分。既视感在裁决不是
confident 时转向图谱节点，只有在经过核实的裁决下才把归档称为「empty」；三个循环都照原样
使用构建好的块。先前的契约是一个带「⚠」的字符串，三处用 `startswith` 解析——标记前打印的
档案会让门失效——后来是一个 enum，被三条手写的 `if/elif` 链各自解读。

**以块为单位，而非整个文件。** 文件按 markdown 标题切分；过长的小节按段落切分
并保留重叠，没有标点的连续文本按长度切分。每个块都会把面包屑（「文件 → H1 →
H2」）一并送入嵌入模型——「嗯，就这么办」这样的块单独存在毫无意义。实测工作图谱：
941 个去重文件约生成 4800 个块，中位数 1686 字符。

这取代了原先「每个文件一个向量、取前 12 000 字符」的做法。对节点而言该假设成立，
对会议逐字稿则完全相反：决定都在结尾做出。同一图谱中有 325 个文件超过该阈值，
**全部内容的 63% 从未进入索引**。此外，尽管 bge-m3 声称支持 8192 个 token，
Ollama 仍会静默截断输入。上限是运行器的物理批大小 2048 个 token（Ollama 0.32+，
2026-09-26 实测：更长的输入返回 HTTP 200，`prompt_eval_count` 为 2048，上限之后的唯一
尾部不改变向量；此前的测量约为 12 300 字符）。这相当于 5–6 千字符的图谱文本；搜索块
（约 4000 字符，在工作图谱上最多 1587 个 token）都在上限之内。

**hidden 标志。** iCloud 会给其容器内的项目打上 `UF_HIDDEN`，而带
`.skipsHiddenFiles` 的 `FileManager` 会不声不响地跳过它们。在工作图谱上，
「Люди」「Системы」「Встречи」以及几乎整个「Документация」就此隐身——遍历器只能
看到 1172 个文件中的 546 个。现在检索完全不看该标志；有意隐藏的目录
（`.obsidian`、`.trash`、`.git`）按名称过滤——这是由用户而非同步机制决定的属性。归档
每写入一场会议就清除该标志；批量遍历（历史迁移、回溯处理）只在边界处清理整个图谱——
第一场会议之前和结束时各一次——遍历中的每场会议只清理自己的文件夹：遍历整个图谱约需
半秒，逐场支付会让完整积压多出约 150 秒。

**文档角色。** 流水线为每场会议产出多份文档，作为「我们决定了什么」的答案，它们
质量差异极大：原始素材（逐字稿、提示、草稿）权重降至 0.7，提炼素材（纪要、摘要、
核心节点）提升至 1.15。原始文本适合引用，最不适合作为答案。

**上下文预算。** 输出有上限：单一来源不超过预算的 40%，剩余额度不足 300 字符的
来源整体丢弃，最强的两个来源分别放在开头与结尾——长上下文的中部注意力会下降。
32K 窗口不是需要填满的目标。

**开销。** 文件仅在 mtime 变化时重新读取与归一化；关键词按 UTF-8 字节匹配，而不
经过带 unicode 归一化的 `String.range(of:)`；片段只为仍有机会进入答案的候选提取。
在工作图谱上，单次查询耗时 0.6-1.1 秒，此前为 1.8-2.5 秒。

### 数字说明了什么

质量以端到端方式衡量（检索 → 综合），对照一组带预期事实的私有问题集；生成温度
固定为零，使基准比较的是改动本身而不是采样噪声。在工作图谱上：

| 改动 | 召回的事实 |
|---|---|
| 每文件一个向量，取前 12 000 字符 | 11 / 14 |
| 每块一个向量 | **13 / 14** |
| 仅对逐字稿降权 | 11 / 14 |
| 按文档角色加权 | **13 / 14** |
| 上下文预算开/关 | 两种情况均为 13 / 14 |

分块索引找回的，恰恰是提问通常关心的那类细节：速率限制、令牌名称、系统缩写
——那些在漫长会议深处只说过一次的东西。

预算在这里没有带来增益，保留它是出于另一个理由：它限制单份逐字稿可以占据多少
上下文，而这组十个问题并不会触发该情形。

在完整构建的索引上（865 个文件、4335 个块），同一基准达到 **14/14**：每一条预期
事实都进入了答案。此前漏掉的两条正是在漫长会议深处只说过一次的细节——一个速率
限制和一个令牌名称。

有一个值得记录的负面结果。在综合提示中加入「逐字保留缩写与错误码」看起来像是
改进（首轮 13/14），但在固定温度后被证明是回退：11/14 对比不加时的 13/14。该
指令促使模型去引用，而不是承认自己不知道。这项改动已被回滚。

## 如何衡量记忆质量

`app/Probes/MemoryBench.swift` 跑的是真实的检索路径——应用所使用的那一条——对照
一组带预期事实的问题，并报告其中有多少事实进入了答案。

    CHAROITE_BENCH=~/path/memory_bench.yaml \
    CHAROITE_GRAPH_DIR=~/path/to/graph \
    CHAROITE_BENCH_ANSWERS=1 \
      swift test --package-path app \
        --filter CharoiteAppLiveProbes.MemoryBench

实时探针位于独立的 Swift 测试 target。CI 与 nightly 会编译该 target，防止签名
腐化——探针的行为只在手动运行时检验——但只执行 `CharoiteAppTests`；缺少私有知识
图谱或本地模型不能伪装成一次成功的产品测试。

不带 `CHAROITE_BENCH_ANSWERS` 时，它只衡量检索交付了什么；带上之后，衡量的是
经过综合的完整路径。报告落在 `/tmp/charoite_bench.txt`，并点名缺失的事实。

问题集留在仓库之外——它关乎真实会议。格式刻意做得极简：

    - q: "关于支付服务商我们决定了什么？"
      must: ["YuPay", "2.8%"]

**生成温度固定为零。** 这不是细节。在默认温度下，同一份代码先后得到 11、13、
再 11（满分 14）——这样的数字无法告诉你改动是否有效，还是只是运气好。正是这个
固定温度的基准抓出了我的一次提示「改进」，它实际上是回退。

`scripts/memory_bench.py` 衡量守护进程的记忆（`src/charoite_graph/graph_search.py`）
——所有者在会议中看到的东西；`--brain` 和 `--legacy` 保留旧的回路，用于前后对比。
它仍然无法回答关于应用内检索的问题，那是另一套 Swift 实现。

## 就绪探针不信任数据文件夹

首次运行的探针用单独的解释器清点缺失的模块和麦克风，其工作目录位于数据文件夹——图谱、
流水线和所有者都往那里写。Python 把当前目录放在 `sys.path` 的第一位，因此放在那里的
`yaml.py` 会以应用的权限执行，顺带破坏探针的 JSON 协议。

这是靠环境而不是 `-I` 标志封住的：`PYTHONSAFEPATH=1` 去掉 cwd，`PYTHONNOUSERSITE=1`
去掉用户目录，`PYTHONPATH`、`PYTHONHOME` 和 `PYTHONSTARTUP` 被清除，因为前者比
`SAFEPATH` 更强，后者会整个替换标准库。`-I` 更宽也更危险：它隐含 `-E`，会让应用用来保持
应用包密封的 `PYTHONPYCACHEPREFIX` 失效——探针会在第一屏就把 `.pyc` 写进已签名的
`Resources`，破坏签名，就像 0.52.0 那样。

探针根本不需要字节码：`PYTHONDONTWRITEBYTECODE=1`，缓存前缀与写入一并去掉。否则前缀会从
另一侧变成导入路径——放在公共缓存目录里的伪造 `.pyc` 会代替模块执行。在内存中编译的一次性
运行耗时 85 毫秒。

测试从两边复现这个漏洞：先让测试台确认劫持确实发生，然后才验证防护能消除它。只检查标志
存在的测试证明的是意图，而不是结果。

## 应用何时得知新版本

版本检查过去只放在服务的 `init` 里，并持有一天的缓存。应用一开就是好几天，于是发布日变成
了等待日：版本早上发布，版本行第二天才知道。

现在回到应用时询问 GitHub，最多每四小时一次，而设置中的「立即检查」按钮绕过节流：人问了
——就回答，而不是「早上已经查过了」。时间戳记在「尝试」上且在请求之前，而不是记在成功的
回答上：否则离线、5xx 和速率限制都会解除节流，每次激活都发一次新的 GET——在共享 IP 上这是
自我维持的配额消耗。同一个时间戳也消除了启动时的重复和重叠的请求。代价是诚实的：失败的
尝试在四小时后或按按钮时重试。这是对公共 API 的普通 GET，不带令牌，也不含任何关于人的数据；
「向 GitHub 查询新版本」开关（`sufler.check_updates`）可以关掉它，`CHAROITE_NO_CLOUD`
也会关掉它——把云端整个关掉的人，不会期待应用为了版本号上网。

代码版本（`git describe`）缓存半分钟：每次激活都起一个子进程太多，但在整个运行期间缓存会
冻结这一行——应用运行时有人手动 `git pull`，「代码已偏离」的标签要么在修复后仍挂着，要么
根本不出现。

## 代码与数据各自的位置

发行代码与工作文件被有意分开。

- **代码** — `src/`、`scripts/`、配置示例。在应用中它与 python 运行环境一起
  位于应用包内（`Charoite.app/Contents/Resources/charoite`）；开发时则位于
  克隆的仓库中。
- **数据** — 录音、逐字稿、日志、模型、`config/config.yaml`。它们属于用户，
  存放在工作文件夹中。

这条边界在配置处有一个锋利的边缘：`config/config.yaml` 属于所有者，取自「数据」根，
而 `config/config.example.yaml` 随发行版提供，取自「代码」根。
`config_loader.load_user_or_example` 正是因此从两个不同的根读取它们；两个根还是同一棵树时
差别看不出来，一旦已安装的入口点指定了自己的根，到数据文件夹里找示例就让模块在导入时崩溃。

工作文件夹由入口点指定。根目录归路径规范（`src/charoite_paths.py`）所有：
`use_data_root(path)` 为进程设定它，`resolve_root` 先回答已指定的根、再看 `CHAROITE_ROOT`，
而这个变量仍是传给子进程的渠道——夜间脚本、索引器、云端工作进程——它们自己推导根。应用启动
守护进程时仍会传入 `CHAROITE_ROOT`。没有它守护进程拒绝启动——退出码 `EXIT_ROOT_UNNAMED`
（5，而不是 2：参数错误时 argparse 返回 2）以及带方法的错误状态——因为入口点是「指定」根，
而不是询问它；从文件位置推导根、再把这个猜测发布给子进程，正是这个拒绝要防止的。没有守护
进程那种通往应用渠道的入口点走同一扇门 `name_data_root_or_exit`：stderr 中的方法和同样的
退出码，应用、launchd 和运行契约探针都读取它。从检出的仓库手动运行可以采用猜测，但只能在
调用本身里明说（`guess_from_code=True`）。只是询问的模块（`resolve_root`）在未指定任何根时
仍会得到一个猜测——代码根——这是推导唯一残留的地方。代码根只从路径规范模块自身的位置推导一次
（`<根>/src/charoite_paths.py`，与 `<根>/scripts/` 同级，导入时校验），`code_root(__file__)` 只检查调用方是否
位于同一棵树中。按每个调用方的位置推导，只在所有调用方都位于根下一级时成立：迁入
包 `src/<包>/x.py` 的模块会把包目录当作代码根，也把同一目录当作数据根（№331；
唯一的包形式——№424）。

答案要询问，而不是记住。模块级的 `ROOT = resolve_root(__file__)`——或作为类字段的同一行——
看起来像是调用规范，其实是一个快照：值在模块被导入时取得，早于入口点来得及指定根。随后进程
悄悄地自相矛盾——一半模块活在指定的根里，一半活在由文件位置推导出的根里。模型租约就是这样
坏掉的：写入方把它存在冻结的根下，健康看门狗却在当前的根下查找，于是「我们的生成正在进行」
回答了「否」。布局守卫把这种形态称为 `snapshot`，并统计导入时执行的一切——类体、`if`、
`try`——除了 `if __name__ == "__main__"`，它在导入时根本不执行。

守卫读的是文本，所以它的覆盖在文本不再是证据的地方终止，而这条边界是点明的而不是暗示的：
导入时调用的方法（`X = A().root()`）、作为值取用的包装（`functools.partial`）和从另一个模块
导入的辅助函数都会悄悄通过。它们由行为来捕捉——`tests/test_backup_offload.py` 中的见证者
在入口点改名之后向每个已注册模块询问根，然后在引擎中的任何地方寻找作为值的「先前」根——
以及在规范开始拒绝未指定的根之后，由拒绝本身来捕捉。用又一条启发式去追赶同一种冻结的每一种
新写法——这条规则就是这样耗掉了五轮评审；形态清单仍是常见情况的廉价检测器，而不是保证。

这个顺序很重要，因为从文件位置推导回答的是另一个问题：「代码」在哪里。代码与数据共用一棵
树时，两个答案只是碰巧一致；从已安装的包里，同一个公式会得到 `site-packages`，流水线会悄悄
读取默认值而不是所有者的设置。所以根是指定的而不是猜的：空值被拒绝，与当前根不同的第二个根
被拒绝，有意的更换走 `use_data_root(..., replace=True)`。写入该变量是一次发布：规范记住之前
那里的值，`forget_data_root()` 会恢复它——但只在变量仍是它自己写的时候（#327）。

原因很简单：应用包已签名且只读。会议录音无法写入其中；而把代码放在用户文件夹
则意味着需要手动克隆——安装又会从终端开始。
