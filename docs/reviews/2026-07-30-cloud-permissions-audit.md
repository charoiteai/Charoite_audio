# Аудит облачных прав Charoite — 30 июля 2026

База аудита: `main` на `f7abf96`. Область: запуск Claude Code после встречи,
границы `cloud_enrich` / `cloud_edit_graph`, prompt injection и сохранность
локальных файлов.

## Резюме

Найден один критичный обход модели разрешений. При
`cloud_enrich: true` и `cloud_edit_graph: false` post-meeting процесс всё равно
получал `Edit`, `Write` и `--permission-mode acceptEdits`. Это противоречило
`PRIVACY*.md`, где `cloud_edit_graph` назван единственным разрешением на запись.

Первый патч закрывает обход и добавляет регрессионные тесты. Остались две
существенные границы, которые стоит закрывать отдельными небольшими PR:
ограничить облачное чтение только подготовленным набором файлов и сделать
правки графа транзакционными, с бэкапом и проверяемым diff.

## CHR-AUD-001 — `cloud_enrich` выдаёт права записи без разрешения

**Критичность:** критическая.  
**Статус:** исправлено в рабочем дереве.

### Условия

```yaml
sufler:
  cloud_enrich: true
  cloud_edit_graph: false
```

После остановки встречи `src/graph_updater.py` запускал Claude с:

```text
--allowedTools Read,Edit,Write,Grep,Glob
--permission-mode acceptEdits
```

Проверки `privacy.cloud_edit_graph_enabled(cfg)` в этой точке не было.
Стенограмма и граф одновременно становились недоверенным вводом агента с
автоматически принятыми правками.

### Исправление

- Команда вынесена в `cloud_enrich_command(..., may_edit=...)`.
- `may_edit` берётся только из `privacy.cloud_edit_graph_enabled(cfg)`.
- Без разрешения доступны только `Read`, `Grep`, `Glob`; `Edit` и `Write`
  явно запрещены, `acceptEdits` отсутствует.
- В read-only режиме Claude возвращает Markdown в stdout, а файл ревизии
  открывает и сохраняет само приложение.
- При явных `cloud_enrich: true` и `cloud_edit_graph: true` прежний режим
  редактирования сохраняется.
- В промпт добавлена граница: текст стенограммы, заметок и графа является
  данными, а не инструкциями.

### Регрессия

`tests/test_cloud_enrich_permissions.py` проверяет оба режима и то, что
решение о записи приходит из `privacy.cloud_edit_graph_enabled`.

## CHR-AUD-002 — облачное чтение не ограничено набором файлов

**Критичность:** высокая.  
**Статус:** открыто.

Read-only устраняет изменение файлов, но `Read/Grep/Glob` по-прежнему
предоставляются процессу Claude Code без технической границы на стенограмму и
граф. Инструкция в промпте снижает вероятность prompt injection, но не является
изоляцией: вредоносный текст встречи может попытаться заставить агента прочитать
другие доступные локальные файлы и включить их содержимое в облачный контекст.

Рекомендуемая следующая правка: собирать временный read-only bundle только из
разрешённых файлов, запускать Claude в нём без доступа к исходному vault и
принимать один структурированный результат.

## CHR-AUD-003 — edit-режим не обеспечивает бэкап и границы записи кодом

**Критичность:** высокая.  
**Статус:** открыто.

Когда `cloud_edit_graph: true`, post-meeting агент редактирует оригинальный
граф напрямую. В этой ветке нет программно обеспеченного бэкапа, allowlist
путей и проверки diff, хотя документы обещают бэкап перед каждой облачной
правкой. Ограничения сейчас сформулированы только в промпте.

Рекомендуемая следующая правка: агент пишет предложения в staging-копию,
приложение валидирует допустимые пути и неприкосновенные секции, сохраняет
бэкап, затем атомарно применяет diff.

## CHR-AUD-004 — фоновый процесс не подтверждает успешное завершение

**Критичность:** средняя.  
**Статус:** открыто.

`Popen` запускается в фоне без timeout и без обработчика exit code. Сообщение
означает только «процесс стартовал». При ошибке read-only отчёт может остаться
пустым или частичным, а пользователь узнает об этом только из лога.

Рекомендуемая правка: отдельный контролируемый worker с timeout, временным
файлом результата, проверкой exit code/минимального формата и атомарным
переименованием в финальное имя.

## CHR-AUD-005 — смысл `cloud_edit_graph` требует уточнения

**Критичность:** средняя.  
**Статус:** решение владельца.

Конфиг и часть документации описывают этот ключ как право ночной ревизии
досье. После исправления он также становится явным правом post-meeting
дообогащения графа. Нужно выбрать один контракт и синхронно закрепить его в
`PRIVACY*`, `config.example*` и тестах:

1. один общий `cloud_edit_graph` для любой облачной записи; или
2. отдельные разрешения на post-meeting и nightly-edit.

Первый вариант проще. Второй даёт пользователю более точный контроль.

Расхождения реализации с предложенным патчем — по делу, не по вкусу:

- право записи берётся внутри `cloud_enrich_command()` у
  `privacy.cloud_edit_graph_enabled(cfg, env)`, а не передаётся флагом
  снаружи: команда физически не может получить права в обход гейта, и это
  проверяется поведением (мусор в значении, рубильник `CHAROITE_NO_CLOUD`), а
  не чтением исходника `main` через `inspect.getsource`;
- рабочая папка — граф в обоих режимах, а не корень репозитория (это и есть
  CHR-AUD-002);
- файлы встречи уходят текстом в запросе, собранные Чароитом, — модели не
  нужен доступ к `transcripts/`.

Из предложенного патча взято: точное равенство состава разрешённых
инструментов, проверка, что `Edit`/`Write` не оказались одновременно в
разрешённых и запрещённых, и маркер-заголовок в файле ревизии.
