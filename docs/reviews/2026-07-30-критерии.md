# Критерии качества Charoite — ревизия 30 июля 2026

Документ отвечает на один вопрос: **по чему судить, стало ли лучше**. Не список
функций, а свойства, которые можно провалить командой. Ниже — как они получены,
семь измерений с проверками, ранжированный список работ, и отдельно то, что
делать сознательно не стоит.

Автор ревизии — автономная сессия Claude, пять часов, без внешнего задания на
темы. Ошибки и догадки помечены как догадки.

---

## Как получены критерии

Три независимых источника, каждый давал своё.

**Рынок.** Что пишут про похожие инструменты — Granola, Otter, Fathom,
Fireflies, самодельные связки Whisper + Obsidian, self-hosted сборки. Искал не
функции, а места, где люди уходят. Сухой остаток:

- Уходят не от нехватки функций, а от **недоверия и трения на входе**. У Otter —
  коллективный иск (август-сентябрь 2025) об использовании записей для обучения
  моделей; в отзывах — списания после отмены и невозможность добраться до
  человека в поддержке. Это ровно та причина, по которой люди приходят к
  локальному инструменту.
- Второй по частоте — **бот в звонке**. Видимый участник-робот раздражает
  клиентов; у Charoite бота нет, и это надо держать как свойство, а не как
  случайность реализации.
- Ценность через месяц — **не транскрипт**. Все обзоры сходятся: сырую
  стенограмму не перечитывают, ценность в сводке, в поиске по прошлым встречам
  и в накопленном контексте («год питчей — это база, одна встреча — точка»).
  Смысл графа знаний тут подтверждается со стороны.
- Про диаризацию есть жёсткая формулировка, которую стоит принять как критерий:
  транскрипт с 99% точностью по словам, но с неверной атрибуцией, **хуже
  бесполезного** — вся ценность заметок в том, кто что обещал. Ошибка
  атрибуции протекает дальше: поручение уходит не тому, сводка наследует
  ошибку, решение записывается на чужое имя.
- У тех, кто выбрал локальное, главная жалоба своя: **установка**. Люди
  бросают на этапе зависимостей (типичная история — полчаса возни с
  WhisperX/pyannote и отказ), и «поставилось за 15 минут» продаётся как
  отдельная фича у конкурентов.

**Свой путь клиента.** Прошёл от чистого листа. Что руками, что по коду —
помечено в приложении в конце документа. Ключевое: `scripts/doctor.py`
действительно хорош (говорит, чего не хватает, и как починить, exit code 1 при
проблемах), а вот команды из README, которыми продукт показывают до первой
встречи, падают трейсбеком — потому что README ставит зависимости в `.venv`, а
запускать предлагает системным `python3`.

**Следы в репозитории.** TODO/FIXME нет ни одного (репозиторий в этом смысле
чистый), пустых тестов нет, `pytest` — 172 зелёных. Зато нашлись расхождения
между тем, что документ обещает, и тем, что читает код: облачных тумблеров
четыре, а PRIVACY.md знает два; один и тот же ключ `cloud_model` имеет в разных
точках выхода разные дефолты; линтер в CI смотрит только `src/`, и в `scripts/`
уже лежат две ошибки уровня F.

## Измерения

### 1. Обещание приватности полно и проверяемо

Единственное свойство, за которым сюда приходят. «Локально по умолчанию»
ценно, только если пользователь может это **перечислить и проверить**: сколько
всего есть путей в облако, каждый ли выключен по умолчанию, действует ли на
каждый рубильник `CHAROITE_NO_CLOUD`. Полнота тут важнее самого дефолта:
незадокументированный тумблер, который шлёт стенограмму, дороже репутации, чем
десять задокументированных.

Как провалить:

```bash
# 1) Каждый тумблер, который читает код, назван в PRIVACY.md
grep -oE 'cloud_[a-z_]+' config/config.example.yaml | sort -u   # сейчас: 4 тумблера + 3 модели
grep -c 'cloud_hints\|cloud_edit_graph' PRIVACY.md              # сейчас: 0 — провал

# 2) Разрешение спрашивают у privacy.py, а не у конфига напрямую
.venv/bin/python -m pytest tests/test_privacy_defaults.py tests/test_cloud_call_sites.py -q
```

Признак провала без теста: в `src/` появилось чтение `cfg["sufler"].get("cloud_…")`
вне `src/privacy.py`. Сейчас такое есть — `src/daemon.py:568`.

### 2. Первые пятнадцать минут — без догадок

Порог, на котором отваливается аудитория локальных инструментов. Требование
жёсткое: **каждая команда, напечатанная в README/SETUP, выполнима в том
окружении, которое эти же README и SETUP создают**. Не «пользователь догадается
подставить `.venv/bin/python`» — догадка и есть дефект.

Как провалить:

```bash
# команды из README прогнать так, как они написаны
python3 scripts/memory_bench.py --demo     # сейчас: ModuleNotFoundError: yaml — провал
python3 scripts/import_meeting.py --help   # сейчас: то же — провал
python3 scripts/doctor.py                  # сейчас: работает (и обязан: он про отсутствие зависимостей)
```

Признак: трейсбек Python в ответ на команду из документации. Диагностика,
которая объясняет, — не провал; трейсбек — провал.

### 3. Один ключ — один смысл и один дефолт

Конфиг у этого продукта — единственная документация по ключам (это уже
зафиксировано в `tests/test_config_example.py`). Продолжение того же правила:
значение по умолчанию в коде обязано совпадать с примером конфига, и один ключ
не может иметь два разных дефолта в двух местах. Иначе пользователь с урезанным
конфигом получает поведение, которого нет ни в одном документе, — и не может
понять, почему.

Как провалить:

```bash
grep -rn 'cloud_model\|cloud_live_model' src/ scripts/ config/config.example.yaml
# сейчас: cloud_model → claude-opus-4-8 (src/graph_updater.py:709, пример конфига)
#         cloud_model → claude-opus-5   (scripts/nightly_claude_cores.py:75,
#                                        scripts/nightly_dossier_review.py:108)
#         cloud_live_model → пример: claude-haiku-4-5-20251001,
#                            код (src/daemon.py:669): claude-sonnet-5
.venv/bin/python -m pytest tests/test_config_example.py -q
```

### 4. Возврат через неделю даёт ответ, а не поиск по свалке

Из рынка: через месяц ценность не в транскрипте, а в ответе на «что мы решили
по X». Значит меряем не наличие поиска, а то, что ответ содержит нужный факт и
что слабое совпадение помечается честно, а не склеивается из чего попало.

Как провалить:

```bash
.venv/bin/python scripts/memory_bench.py --demo   # сейчас 3/3; порог провала — треть кейсов
.venv/bin/python scripts/memory_bench.py          # на своём графе
```

Признак: ответ уверенный, а факта в нём нет. Или наоборот — «⚠ в архиве нет»
там, где источник есть.

### 5. Кто что сказал — не угадывается

Атрибуция либо точна, либо честно обезличена («Собеседник 2»). Подставлять имя
по догадке нельзя: ошибка протекает в поручения, сводки и граф. Это то
измерение, где продукт уже сильнее рынка, и терять его дороже, чем не добавить
новую функцию.

Как провалить:

```bash
.venv/bin/python -m pytest tests/test_audio_capture.py tests/test_cut_overlap.py -q
grep -n '_names\|опозна' src/main.py src/daemon.py   # имя ставится только по «меня зовут…»
```

Признак: в стенограмме стоит имя человека, который в этот момент не
представлялся и чей голос не был размечен.

### 6. Деградация всегда названа вслух

Локальный продукт постоянно работает в неполной комплектации: нет модели
диаризации, нет `bge-m3`, лежит brain-компаньон, мало RAM. Правило: каждая
такая нехватка **проговаривается**, а не превращается в тихо ухудшенный
результат. `doctor.py` и строка бенча «контур поиска: локальный фолбэк (brain
лежит)» — образцы, к которым надо тянуть остальное.

Как провалить:

```bash
.venv/bin/python scripts/doctor.py; echo "exit=$?"   # exit 1 при «✗», рецепт на каждый пункт
.venv/bin/python scripts/memory_bench.py --demo | head -1   # какой контур поиска реально работал
```

Признак: продукт отдал результат хуже обычного и ничего не сказал.

### 7. Гигиена, которую проверяет машина, а не память автора

У проекта три языка документации, три файла-примера конфига, Python + Swift, и
всё это правится одним человеком. Единственный способ не разъехаться —
инвариант, зашитый в тест или CI. Измерение: **любое правило, которое здесь
названо, имеет сторожа**; правило без сторожа считается ненадёжным.

Как провалить:

```bash
.venv/bin/python -m pytest tests/ -q                            # сейчас 172 passed
.venv/bin/ruff check --select E9,F src/ scripts/ tests/          # сейчас 2 ошибки в scripts/
```

Признак: CI зелёный, а ошибка находится руками за минуту (сейчас именно так:
`ruff` в CI смотрит только `src/`).

## Ранжированный список работ

Порядок — по отношению «цена доверия пользователя / стоимость работы».

### 1. PRIVACY.md знает два тумблера из четырёх (измерение 1)

Есть `cloud_enrich`, `cloud_live`, `cloud_hints`, `cloud_edit_graph`.
`PRIVACY.md`/`.ru`/`.zh` перечисляют первые два. README называет три —
без `cloud_hints`. При этом `cloud_hints` по природе самый «текучий»: по
описанию в `docs/FEATURES.ru.md:149-154` он шлёт стенограмму в облако **на
каждую подсказку**, то есть постоянным потоком, а не одним пакетом после стопа.

Человек получает: полный, честный список того, что может уйти с машины, в том
самом файле, который читают ради доверия.

Цена: правка трёх PRIVACY + сторож, который валится, когда в конфиге появляется
новый `cloud_*`, не названный в PRIVACY.md.

Подтверждение: тест сверяет множество `cloud_*` из `config.example.yaml` со
списком в PRIVACY.md; добавление тумблера без документации ломает CI.

### 2. Облачные тумблеры под одним гейтом (измерения 1, 7)

`src/privacy.py` — объявленная единственная точка решения, и `KEYS` там —
только `("cloud_live", "cloud_enrich")`. `cloud_hints` читается напрямую в
`src/daemon.py:568`, а сторож обхода (`tests/test_privacy_defaults.py:36`)
знает те же два имени, поэтому обход не видит.

Сейчас дырки нет: строка 569 требует ещё и `cloud_live`, а он уже прошёл через
`privacy.cloud_live_enabled()` (`src/daemon.py:490`), поэтому рубильник
работает. Но держится это на одном `and` в одной строке и не закрыто ни одним
тестом: любая правка, которая сделает облачные подсказки независимыми от
`cloud_live` (а это выглядит как естественное развитие — отдельный тумблер
затем и вводили), молча выведет путь из-под рубильника.

Человек получает: гарантию, что `CHAROITE_NO_CLOUD=1` действительно выключает
всё, и в будущем тоже.

Цена: `cloud_hints_enabled()` в `privacy.py`, вызов вместо чтения конфига в
`daemon.py`, расширение регулярки сторожа на все ключи `cloud_*`.

Подтверждение: тест «рубильник побеждает конфиг» для каждого тумблера +
структурный тест «никто не читает `cloud_*` в обход privacy».

### 3. Команды из README падают трейсбеком (измерение 2)

`README.ru.md:90-91` (и англ./кит. версии) предлагают
`python3 scripts/memory_bench.py --demo` и
`python3 scripts/import_meeting.py …`, тогда как зависимости по этому же README
ставятся в `.venv`. Системный `python3` их не видит:
`ModuleNotFoundError: No module named 'yaml'`. Это первые две команды, которыми
продукт показывают до первой встречи, — то есть трейсбек ровно там, где
формируется первое впечатление.

Человек получает: демо, которое запускается с первого раза.

Цена: правка README ×3 на `.venv/bin/python` + понятное сообщение вместо
трейсбека, когда скрипт всё-таки запущен не тем интерпретатором (образец —
`doctor.py`, он специально написан без внешних зависимостей).

Подтверждение: тест вытаскивает из README команды вида
`python3 scripts/*.py` и требует, чтобы каждая либо не требовала внешних
пакетов, либо была написана через `.venv/bin/python`.

### 4. Один ключ — два дефолта (измерение 3, упрощение)

`cloud_model`: `claude-opus-4-8` в `src/graph_updater.py:709` и в примерах
конфига, `claude-opus-5` в `scripts/nightly_claude_cores.py:75` и
`scripts/nightly_dossier_review.py:108`. `cloud_live_model`: пример конфига
обещает `claude-haiku-4-5-20251001`, `src/daemon.py:669` без ключа берёт
`claude-sonnet-5` — другая модель другого класса.

Человек получает: то, что написано в примере конфига, и одинаковое поведение
на всех шагах.

Цена: свести дефолты в одно место (там же, где живёт решение об облаке),
литералы из точек выхода убрать.

Подтверждение: тест сверяет дефолты в коде с `config.example.yaml`; расхождение
валит CI.

### 5. Мёртвый код в `scripts/`, которого не видит CI (измерения 7, упрощение)

`ruff check --select E9,F src/ scripts/ tests/` находит
`scripts/import_meeting.py:202` (неиспользуемый `numpy`) и
`scripts/morning_brief.py:126` (переменная `head`, которую никто не читает).
В CI линтер запускается только по `src/`, поэтому обе живут в main.

Человек получает: чуть меньше кода, который надо понимать; и линтер, который
ловит это до ревью.

Цена: удалить две строки; охват линтера в CI — отдельным решением, потому что
правка workflow за пределами мандата этой сессии (см. «не делаю»).

Подтверждение: `ruff check --select E9,F src/ scripts/ tests/` чист.

### 6. `src/main.py:3` учит запускать из чужой папки — и это утечка (измерения 2, 1)

Docstring CLI велит перейти в папку приватной сборки проекта и запускать оттуда.
Публичный репозиторий называется иначе, так что читатель исходника получает
инструкцию, которая у него не работает.

Хуже другое: имя приватной сборки — маркер из списка обезличивания
(`scripts/check_private_markers.py`, список вне git). Страж проверяет только
файлы в индексе текущего коммита, поэтому строку, попавшую в main до того, как
маркер внесли в список, он не видит и сегодня — а лежит она в публичном
репозитории. Проверено в этой сессии: страж заблокировал новый файл с той же
строкой и промолчал про существующую.

Человек получает: публичный репозиторий без следов приватной сборки и стража,
который умеет проверить не только диф, но и всё дерево.

Цена: одна строка в docstring; полное сканирование — режим `--all` у стража
(дешёвый флаг, тот же список, тот же вывод).

Подтверждение: `python3 scripts/check_private_markers.py --all` чист и валится,
если маркер внесён в любой файл дерева, не только в новый.

## Ревизия по этим критериям (дополнение того же дня)

Проверка кода против измерений выше. Две находки оказались тяжелее всего, что
было в первом списке, и сдвинули порядок работ: они портят данные в
**дефолтной конфигурации** — у того, кто поставил продукт и не докладывал
модель диаризации.

### Р1. Имя владельца присваивается собеседнику (измерение 5) — критично

`src/daemon.py:1044` и `src/daemon.py:1065`: имя, предложенное моделью,
отбраковывается, если совпало с владельцем, — но сравнивается оно с
`user_name` **целиком**:

```python
owner_name = (cfg["sufler"].get("user_name") or "").strip().lower()   # :989
...
and name.lower() != owner_name                                        # :1044, :1065
```

`config/config.example.yaml:34` просит «ваше имя», `docs/SETUP.ru.md:25` — то
же, и человек пишет «Имя Фамилия»: это естественное чтение просьбы.

Сценарий отказа. `user_name: "Игорь Ветров"` (имена здесь и ниже — из
встроенного демо-графа), встреча один на один, модели диаризации нет.
Собеседник говорит: «Игорь, привет, ты смету смотрел?». Опознаватель видит имя
«Игорь» в стенограмме, сравнивает: `"игорь" != "игорь ветров"` — проверка
владельца пропускает. `rename_speaker` меняет метку **задним числом во всех
блоках** (`src/main.py:171-178`): вся встреча подписана так, будто собеседник и
есть владелец. Дальше это уходит в минутки, поручения и граф — «Игорь обещал
прислать смету», хотя обещал собеседник. Ровно та протечка, из-за которой рынок
считает неверную атрибуцию хуже отсутствия транскрипта.

### Р2. Гвард «обращение ≠ говорящий» есть только в одной из двух ветвей (измерение 5)

`name_loop` в `src/daemon.py` разветвляется: мультиспикерная (есть трекер
голосов) и одиночная (`elif not named:`, строки 1054-1069).

В мультиспикерной стоит гвард `own_only` (`:1028-1042`) с прямым указанием,
откуда он взялся: «„Саш, ну а кто…“ помечало говорящего Сашей — 21.07». То
есть ошибка наблюдалась вживую и была закрыта — **в одной ветке из двух**.
В одиночной ветке гварда нет: там только промпт, просящий модель не путать
обращение с самопредставлением, и лёгкая модель (`llm.small`).

Одиночная ветка — это не экзотика, а **поведение по умолчанию**:
`spk_tracker` остаётся `None`, пока в `models/diar/embedding.onnx` не положен
ERes2Net (`src/daemon.py:330-339`), а он не входит в поставку — `doctor.py`
честно пишет «диаризации нет». Значит слабейшая ветка работает у всех, кто
только что поставил продукт.

Заодно ветки разошлись в мелочах: минимальная длина имени 3 против 2,
нормализация падежей по известным людям (`known_first`, «Полин→Полина») есть
только в мультиспикерной.

### Р3. Отсутствие модели диаризации не проговаривается (измерение 6)

`src/daemon.py:332-342`: если `live_diarize` включён (дефолт `true`), но файла
модели нет, ветка `if emb_model.exists()` просто не выполняется — и **ни одного
сообщения**. Исключение бы сообщили («живая диаризация недоступна: …»), а
штатное отсутствие модели — нет.

Сценарий: человек читает в README про «Собеседник 1/2/…» по голосам, ставит
продукт, ведёт встречу с тремя участниками, получает всех троих под одной
канальной меткой — и никакого объяснения в интерфейсе. Диагноз есть, но в
другом месте и только если догадаться запустить `doctor.py`.

### Р4. Приватные маркеры остались в публичном дереве (измерение 1)

`scripts/check_private_markers.py` проверяет только файлы в индексе коммита.
Полный проход по `git ls-files` тем же списком маркеров даёт две живые строки в
`main`: `src/main.py:3` и `src/mcp_server.py:6` — обе попали до того, как
маркер внесли в список, и страж их не увидит никогда.

Проверено в этой сессии: страж заблокировал новый файл с той же строкой
(документ критериев пришлось переписать) и промолчал про существующие.

### Что изменилось в приоритетах

Порядок работ после ревизии:

1. **Р1 + Р2 + Р3 одним пунктом** — атрибуция говорящих в дефолтной
   конфигурации. Было шестым (в первом списке диаризацию я вообще записал в
   «не трогаю»), стало первым: портится не удобство, а содержание стенограммы
   и графа, причём у нового пользователя. Оговорка из «не делаю» остаётся в
   силе — пороги и сам алгоритм диаризации не трогаю, правлю только логику
   доверия к имени, которая проверяется на строках, без звука.
2. Пункт 1 первого списка (PRIVACY.md знает два тумблера из четырёх) + пункт 2
   (`cloud_hints` под гейт `privacy.py`) — их естественно делать одним PR.
3. Пункт 3 (команды README) + Р4 (маркеры в дереве) — тоже один PR: оба про
   документацию как часть продукта, оба дешёвые.
4. Пункты 4 и 5 (дефолты моделей, мёртвый код) — упрощение, если останется
   время.

## Что сознательно НЕ делаю

- **Не включаю ничего облачного по умолчанию** и не «улучшаю» пороги
  `tier3_auto_apply`, `record_keep_days`, `deja_vu_margin`. Дефолты приватности
  — предмет решения владельца, а не ревизии.
- **Не расширяю охват `ruff` в CI сам.** Это правка `.github/workflows/*`,
  которую сессия себе запретила, если пункт не прямо про CI. Мёртвый код удалю,
  а расширение охвата — предложение владельцу (одна строка в `ci.yml`:
  добавить `scripts/ tests/` к цели линтера; риск — придётся сразу чинить
  накопившееся, поэтому это его решение, а не моё).
- **Не трогаю живую диаризацию и её пороги.** Измерение 5 — сильная сторона
  продукта, а проверить правку по-настоящему нельзя без реального звука и
  модели эмбеддингов; править на ощупь то, что работает, — худший из размеров.
  Уточнение после ревизии (Р1-Р3): сам алгоритм диаризации, `threshold` и
  склейку каналов не трогаю по-прежнему. Правлю только логику доверия к
  ОПОЗНАННОМУ ИМЕНИ — она работает со строками стенограммы, проверяется без
  звука, и именно там портятся данные.
- **Не свожу `SUFLER_NO_CLOUD` к одному имени.** Выглядит как упрощение, но
  ломает рубильник у тех, кто уже вписал его в launchd-плист или профиль
  оболочки. Два имени в одном списке `privacy.KILL_SWITCHES` стоят дешевле, чем
  один сломанный офлайн-запуск.
- **Не добавляю зависимостей.** Ни одна из работ выше их не требует.
- **Не берусь за просмотрщик графа без Obsidian, локализацию интерфейса и
  доставку с телефона по Wi-Fi** (ROADMAP). Это недели, а не часы; надкусить их
  в автономной сессии — сделать хуже, чем не начинать.
- **Не переписываю тесты, которые мешают.** Ни один не мешал: наоборот, три из
  них (`test_privacy_defaults`, `test_cloud_call_sites`, `test_config_example`)
  прямо подсказали, где инвариант неполон.
